# Mileage & Forecast Calculations — TO-BE (MVP)

**Date**: 2026-01-14  
**Version**: MVP  
**Purpose**: Specification for unified daily mileage rate calculation and service item forecast  
**Status**: Target specification (not implemented)

---

## Goals

1. **Единый алгоритм расчёта среднего пробега** для всех экранов (Home, Items List, Item Details)
2. **Rolling 60 days window** — использовать только последние 60 календарных дней для расчёта
3. **Day-bucket правило** — корректная обработка множественных записей в один день
4. **Единый источник времени** — все расчёты используют один `now`/`today`
5. **Автоматическое обновление time-mode элементов** — daysLeft уменьшается каждый день без новых записей пробега
6. **Чёткое правило limiting factor** — для элементов с обоими интервалами (km и time)

---

## Non-goals

1. Фоновые задачи и cron для пересчёта (MVP использует пересчёт "на чтение")
2. Сложные алгоритмы машинного обучения для прогноза
3. Учёт сезонности и трендов (линейная экстраполяция достаточна)
4. Множественные fallback стратегии (только один простой fallback)
5. Настройка пользователем параметров расчёта (фиксированные правила MVP)

---

## Definitions

### Термины

- **`now`** — единый источник текущего времени (например, `appNow`)
- **`today`** — локальная календарная дата, полученная из `now` в таймзоне пользователя
- **`rolling 60 days`** — период от `(today - 60 дней)` до `today` включительно
- **`day bucket`** — группа записей пробега, относящихся к одной локальной календарной дате
- **`active day`** — календарный день, в котором есть хотя бы одна запись пробега
- **`daily rate`** или **`avgKmPerDay`** — средний пробег в километрах за календарный день
- **`km-mode`** — элемент обслуживания, интервал которого задан в километрах
- **`time-mode`** — элемент обслуживания, интервал которого задан в календарных днях
- **`limiting factor`** — фактор (km или time), который наступит раньше и определяет статус элемента

### Единицы измерения

- Пробег: километры (целое число)
- Время: календарные дни (целое число, округление вверх для прогнозов)
- Интервалы: километры для km-mode, календарные дни для time-mode

## Inputs (data model assumptions)

### Odometer entries

```typescript
interface OdometerEntry {
  id: string;
  occurred_at: string;  // ISO timestamp (пользовательская дата/время)
  mileage_km: number;     // Показание одометра
  note: string | null;
  created_at: string;    // Системный timestamp (не используется в расчётах)
}
```

**Важно**: В расчётах используется только `occurred_at` (пользовательская дата), не `created_at`.

### Service items

```typescript
interface ServiceItem {
  id: string;
  title: string;
  interval_km: number | null;      // Интервал в км (для km-mode)
  interval_days: number | null;     // Интервал в днях (для time-mode)
  notify_before_days: number;        // Порог для статуса SOON (в днях)
  measurement_mode: 'km' | 'calendar';  // Режим измерения
  // ... другие поля
}
```

### Service events

```typescript
interface ServiceEvent {
  id: string;
  service_item_id: string;
  occurred_at: string;  // ISO timestamp последней замены
  mileage_km: number;     // Пробег на момент замены
  note: string | null;
}
```

## Daily mileage rate (rolling 60 days)

### Алгоритм расчёта

#### Шаг 1: Определение окна

1. Получить `today` из единого источника `now` (локальная календарная дата)
2. Вычислить `cutoffDate = today - 60 календарных дней`
3. Отфильтровать записи: `entry.occurred_at >= cutoffDate AND entry.occurred_at <= now`
   - Исключить записи с датой в будущем (относительно `now`)
   - Включить записи с датой в прошлом (в пределах 60 дней)

#### Шаг 2: Day-bucket группировка

1. Для каждой записи определить локальную календарную дату: `entryDate = localDate(entry.occurred_at)`
2. Сгруппировать записи по `entryDate` (day buckets)
3. Для каждого day bucket:
   - `startKmDay = MIN(mileage_km)` среди записей этого дня
   - `endKmDay = MAX(mileage_km)` среди записей этого дня
   - `dayDeltaKm = endKmDay - startKmDay` (может быть 0, если все записи в один день имеют одинаковый пробег)

#### Шаг 3: Вычисление среднего пробега

1. Найти первый активный день в окне: `firstDay = MIN(entryDate)` среди всех day buckets
2. Найти последний активный день в окне: `lastDay = MAX(entryDate)` среди всех day buckets
3. Вычислить календарный span: `daysSpan = (lastDay - firstDay) + 1` (инклюзивно)
4. Вычислить общий пробег: `totalKm = endKmDay(lastDay) - startKmDay(firstDay)`
5. Вычислить средний пробег: `avgKmPerDay = totalKm / daysSpan`

**Важно**: Используется общий пробег от первого до последнего дня, а не сумма внутридневных дельт.

#### Шаг 4: Валидация результата

**Условия валидности**:
- `daysSpan >= 2` (минимум 2 разных календарных дня с данными)
- `totalKm > 0` (пробег увеличился)

Если условия не выполнены → результат: `{ dailyRate: null, reason: 'insufficient data' }`

Если условия выполнены → результат: `{ dailyRate: avgKmPerDay, daysSpan, firstDay, lastDay }`

### Fallback (14 активных дней)

**Триггер**: Если rolling 60 days дал `insufficient data`

**Алгоритм**:
1. Найти все активные дни (дни с записями) за весь период данных
2. Взять последние 14 активных дней (по дате, не по количеству записей)
3. Если активных дней < 2 → `insufficient data`
4. Иначе:
   - `firstDay = первый из 14 активных дней`
   - `lastDay = последний из 14 активных дней`
   - `daysSpan = (lastDay - firstDay) + 1` (календарный span, инклюзивно)
   - `totalKm = endKmDay(lastDay) - startKmDay(firstDay)`
   - `avgKmPerDay = totalKm / daysSpan`
   - Результат: `{ dailyRate: avgKmPerDay, daysSpan, firstDay, lastDay, isFallback: true }`

## Multiple entries per day handling (day-bucket rule)

### Правило

**Все записи в один календарный день обрабатываются как один day bucket.**

**Внутри дня**:
- Берётся минимальный пробег дня (`startKmDay`) и максимальный пробег дня (`endKmDay`)
- Внутридневной пробег `dayDeltaKm = endKmDay - startKmDay` может быть 0 (если все записи одинаковые)
- Внутридневной пробег НЕ влияет на `daysSpan` (span считается по календарным дням)

**Пример**:
- День 1: записи 10000, 10050, 10100 → `startKmDay = 10000`, `endKmDay = 10100`, `dayDeltaKm = 100`
- День 2: запись 10200 → `startKmDay = 10200`, `endKmDay = 10200`, `dayDeltaKm = 0`
- `daysSpan = (День 2 - День 1) + 1 = 2`
- `totalKm = 10200 - 10000 = 200`
- `avgKmPerDay = 200 / 2 = 100 км/день`

**Важно**: Количество записей в день не влияет на расчёт. 10 записей в один день дают тот же результат, что и 1 запись.

## Forecast model

### Km-based service items (km-mode)

#### Входные данные

- `lastServiceKm`: пробег на момент последней замены (из `lastEvent.mileage_km`)
- `intervalKm`: интервал замены в километрах (из `serviceItem.interval_km`)
- `currentKm`: текущий максимальный пробег (из `getMaxMileageEntry()`)
- `dailyRate`: средний пробег в км/день (из расчёта rolling 60 days)

#### Расчёт оставшегося пробега

```
nextServiceKm = lastServiceKm + intervalKm
kmLeft = nextServiceKm - currentKm
```

**Результат**:
- Если `kmLeft > 0`: осталось `kmLeft` км до замены
- Если `kmLeft <= 0`: просрочено на `|kmLeft|` км

#### Расчёт оставшихся дней

**Условие**: `dailyRate !== null AND dailyRate > 0`

**Формула**:
```
daysLeft = ceil(kmLeft / dailyRate)
```

**Результат**:
- Если `dailyRate` валиден: `daysLeft` (может быть отрицательным, если просрочено)
- Если `dailyRate` невалиден: `daysLeft = null` (показывать "недостаточно данных")

#### Расчёт даты следующей замены

**Условие**: `daysLeft !== null`

**Формула**:
```
nextReplacementDate = today + daysLeft
```

**Результат**: Дата следующей замены (может быть в прошлом, если просрочено)

---

### Time-based service items (time-mode)

#### Входные данные

- `lastServiceDate`: дата последней замены (из `lastEvent.occurred_at`, приведённая к локальной дате)
- `intervalDays`: интервал замены в календарных днях (из `serviceItem.interval_days`)
- `today`: текущая локальная календарная дата (из единого источника `now`)

#### Расчёт даты следующей замены

```
dueDate = lastServiceDate + intervalDays
```

**Результат**: Календарная дата, когда должна произойти следующая замена

#### Расчёт оставшихся дней

```
daysLeftTime = (dueDate - today)
```

**Результат**:
- Если `daysLeftTime > 0`: осталось `daysLeftTime` дней
- Если `daysLeftTime <= 0`: просрочено на `|daysLeftTime|` дней

#### Автоматическое обновление

**Правило**: `daysLeftTime` должен пересчитываться при каждом отображении экрана, используя текущий `today`.

**Следствие**: Если пользователь открывает экран на следующий день (без новых записей пробега), `daysLeftTime` автоматически уменьшается на 1.

**Реализация**: Пересчёт происходит "на чтение" (при рендере страницы), не требуется фоновых задач.

---

### Mixed / limiting factor rule

#### Условие применения

Элемент имеет оба интервала: `interval_km !== null AND interval_days !== null`

#### Расчёт обоих критериев

1. **Km-критерий**:
   - `nextServiceKm = lastServiceKm + intervalKm`
   - `kmLeft = nextServiceKm - currentKm`
   - `daysLeftKm = ceil(kmLeft / dailyRate)` (если `dailyRate` валиден)
   - `dueByKmDate = today + daysLeftKm` (если `daysLeftKm !== null`)

2. **Time-критерий**:
   - `dueDate = lastServiceDate + intervalDays`
   - `daysLeftTime = dueDate - today`
   - `dueByTimeDate = dueDate`

#### Определение limiting factor

**Правило**: Limiting factor — это критерий, который наступит раньше.

**Алгоритм**:
1. Если `dueByKmDate !== null AND dueByTimeDate !== null`:
   - `limitingFactor = (dueByKmDate < dueByTimeDate) ? 'km' : 'time'`
   - `primaryDueDate = MIN(dueByKmDate, dueByTimeDate)`
2. Если только один критерий доступен:
   - `limitingFactor = доступный критерий`
   - `primaryDueDate = соответствующий dueDate`

#### Отображение в UI

**Правило**: Показывать оба значения, но выделять limiting factor как основной.

**Пример отображения**:
- Основной: "Осталось 50 км / ~3 дня" (limiting factor: km)
- Вторичный: "По времени: 15 дней" (time-критерий)

## Time / 'today' source and consistency rules

### Единый источник времени

**Правило**: Вся система использует один источник `now` (например, `appNow`).

**Запрещено**:
- Смешивание `new Date()` в одном месте и `appNow` в другом
- Использование `created_at` вместо `occurred_at` для расчётов
- Разные источники времени на разных экранах

### Получение локальной даты

**Правило**: `today` определяется в локальной таймзоне пользователя (как в UI).

**Формула**:
```
today = localDate(now)
```

Где `localDate()` — функция приведения timestamp к локальной календарной дате (без времени).

### Консистентность между экранами

**Правило**: Home, Items List, Item Details должны использовать:
1. Один и тот же источник `now`
2. Одну и ту же функцию расчёта `dailyRate`
3. Одни и те же правила для `today`

**Результат**: Одинаковые входные данные дают одинаковые результаты на всех экранах.

## Recalculation and refresh rules

### Когда пересчитывать

#### 1. При добавлении/изменении записи пробега

**Действия**:
- Пересчитать `dailyRate` (rolling 60 days)
- Пересчитать все km-mode прогнозы (используя новый `dailyRate`)
- Пересчитать все time-mode прогнозы (используя новый `today`, если изменился день)

**Триггер**: После успешного сохранения новой записи пробега

#### 2. При добавлении/изменении service event

**Действия**:
- Пересчитать прогноз соответствующего элемента (новый `lastServiceDate` или `lastServiceKm`)
- Если элемент имеет оба интервала — пересчитать limiting factor

**Триггер**: После успешного сохранения service event

#### 3. При изменении настроек service item

**Действия**:
- Пересчитать прогноз элемента (новые `intervalKm` или `intervalDays`)
- Если изменился `measurement_mode` — пересчитать по новым правилам

**Триггер**: После успешного сохранения изменений service item

#### 4. При открытии экрана/рендере

**Действия**:
- Пересчитать `dailyRate` (rolling 60 days от текущего `today`)
- Пересчитать все time-mode `daysLeftTime` (от текущего `today`)
- Пересчитать все km-mode прогнозы (если изменился `dailyRate`)

**Триггер**: При каждом рендере страницы (server-side или client-side)

### MVP note

**В MVP достаточно пересчёта "на чтение/рендер" (derived data).**

**Не требуется**:
- Фоновые задачи для пересчёта
- Cron jobs
- Периодические обновления в реальном времени

**Достаточно**: Пересчёт при каждом запросе страницы или после изменения данных.

## Edge cases

### 1. Все записи в один день

**Сценарий**: В rolling 60 days есть записи только за один календарный день.

**Обработка**:
- `daysSpan = 1` (один день)
- Условие `daysSpan >= 2` не выполнено → `insufficient data`
- Попытка fallback на 14 активных дней

### 2. Записи с одинаковым пробегом

**Сценарий**: Все записи в окне имеют одинаковый `mileage_km`.

**Обработка**:
- `totalKm = 0`
- Условие `totalKm > 0` не выполнено → `insufficient data`

### 3. Записи в будущем

**Сценарий**: Есть записи с `occurred_at > now`.

**Обработка**:
- Исключить такие записи из расчёта (фильтр: `entry.occurred_at <= now`)
- Использовать только записи до текущего момента

### 4. Нет записей пробега

**Сценарий**: В базе нет записей пробега или все записи старше 60 дней.

**Обработка**:
- `dailyRate = null` (insufficient data)
- Все km-mode прогнозы показывают "недостаточно данных"
- Time-mode прогнозы работают нормально (не зависят от пробега)

### 5. Нет lastEvent для элемента

**Сценарий**: Элемент обслуживания не имеет последнего события замены.

**Обработка**:
- Статус: `UNKNOWN`
- `daysLeft = null`, `kmLeft = null`
- Показывать "нет данных о последней замене"

### 6. dailyRate = 0 или отрицательный

**Сценарий**: Расчёт дал `dailyRate <= 0` (не должен происходить при валидации).

**Обработка**:
- Считать `dailyRate` невалидным
- `daysLeft = null` для km-mode элементов
- Показывать "недостаточно данных"

### 7. Переход через полночь (time-mode)

**Сценарий**: Пользователь открывает экран на следующий день.

**Обработка**:
- `today` обновляется автоматически (из `now`)
- `daysLeftTime` пересчитывается и уменьшается на 1
- UI обновляется без необходимости новых записей пробега

## Acceptance criteria (testable scenarios)

### Сценарий 1: Множественные записи в один день (day-buckets)

**Входные данные (записи пробега)**:

| Local date | Time | mileage_km |
|-----------:|:-----|-----------:|
| 2025-01-01 | 10:00 | 10000 |
| 2025-01-01 | 15:00 | 10050 |
| 2025-01-01 | 20:00 | 10100 |
| 2025-01-02 | 10:00 | 10200 |

**Ожидаемые промежуточные значения**:
- День 2025-01-01: `startKmDay = 10000`, `endKmDay = 10100`
- День 2025-01-02: `startKmDay = 10200`, `endKmDay = 10200`

**Ожидаемый результат**:
- `firstDay = 2025-01-01`, `lastDay = 2025-01-02`, `daysSpan = 2`
- `totalKm = 10200 - 10000 = 200`
- `avgKmPerDay = 200 / 2 = 100`

**Критерий**: Добавление/удаление внутренних записей в 2025-01-01 (при неизменных `startKmDay`/`endKmDay`) не меняет `avgKmPerDay`.

---

### Сценарий 2: Редкий ввод (2 записи за неделю → календарный span)

**Входные данные**:

| Local date | mileage_km |
|-----------:|-----------:|
| 2025-01-01 | 10000 |
| 2025-01-08 | 10500 |

**Ожидаемый результат**:
- `firstDay = 2025-01-01`, `lastDay = 2025-01-08`
- `daysSpan = 8` (инклюзивно)
- `totalKm = 10500 - 10000 = 500`
- `avgKmPerDay = 500 / 8 = 62.5`

**Критерий**: `daysSpan` считается по календарным дням между `firstDay` и `lastDay`, а не по числу записей.

---

### Сценарий 3: Rolling 60 days ограничивает старую историю

**Входные данные**:

| Local date | mileage_km | In rolling window? |
|-----------:|-----------:|:-------------------|
| 2024-01-01 | 50000 | no (older than 60d) |
| 2024-12-01 | 55000 | yes |
| 2025-01-08 | 56000 | yes |

`today = 2025-01-08`, `cutoffDate = 2024-11-09` (60 календарных дней назад)

**Ожидаемый результат**:
- Запись 2024-01-01 исключена (старше 60 дней)
- `firstDay = 2024-12-01`, `lastDay = 2025-01-08`
- `daysSpan = 39` (календарных дней)
- `totalKm = 56000 - 55000 = 1000`
- `avgKmPerDay = 1000 / 39 ≈ 25.6 км/день`

**Критерий**: Записи старше окна не влияют на `avgKmPerDay`.

---

### Сценарий 4: Time-mode автоматическое уменьшение daysLeft

**Входные данные (service item)**:

- `measurement_mode = 'calendar'`\n+- `interval_days = 365`\n+- `lastServiceDate = 2024-01-01`\n+
**Ожидаемые значения по дням**:

| today | dueDate (= lastServiceDate + 365d) | daysLeftTime (= dueDate - today) |
|------:|:-----------------------------------|---------------------------------:|
| 2025-01-01 | 2025-01-01 | 0 |
| 2025-01-02 | 2025-01-01 | -1 |

**Ожидаемый результат**:
- При открытии экрана на день 2, `daysLeftTime` автоматически уменьшается на 1
- Статус меняется с OK на OVERDUE

**Критерий**: `daysLeftTime` зависит от `today` и пересчитывается при каждом отображении/рендере.

---

### Сценарий 5: Km-mode с валидным dailyRate

**Входные данные**:

| Field | Value |
|------|------:|
| interval_km | 10000 |
| lastServiceKm | 50000 |
| currentKm | 55000 |
| dailyRate | 50 |
| today | 2025-01-01 |

**Ожидаемый результат**:
- `nextServiceKm = 50000 + 10000 = 60000`
- `kmLeft = 60000 - 55000 = 5000`
- `daysLeft = ceil(5000 / 50) = 100 дней`
- `nextReplacementDate = today + 100`

**Критерий**: При валидном `dailyRate` вычисляются `daysLeft` и `nextReplacementDate` по формулам.

### Сценарий 6: Консистентность между экранами (единые правила)
