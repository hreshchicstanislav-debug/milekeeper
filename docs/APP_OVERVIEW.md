# Обзор приложения MileKeeper

## Назначение

PWA (Progressive Web App) для отслеживания пробега автомобиля и напоминаний о техническом обслуживании. Single-tenant приложение (один пользователь, один автомобиль).

## Технологии

- **Frontend**: Next.js 16 (React 19), TypeScript
- **Backend**: Supabase (PostgreSQL)
- **Deployment**: Vercel
- **Язык интерфейса**: Русский

## Экраны приложения

### 1. Главная страница (`/`)

**Информация**:
- **Текущий пробег** — максимальное значение `mileage_km` из всех записей одометра
- **Блок "Скоро обслуживание"** — до 5 элементов, требующих внимания:
  - Элементы со статусом `OVERDUE` (просрочено)
  - Элементы со статусом `SOON` (скоро замена)
  - Сортировка: сначала `OVERDUE`, затем `SOON` по срочности
  - Для каждого элемента показывается: название, остаток (км или дни), прогноз дней
  - Показывается средний темп езды (км/день) с пометкой "(примерно)" если используется fallback
- **Блок "Нужно отметить первую замену"** — элементы без истории замен (`lastEvent === null`), до 5 штук
- **Кнопка "Добавить пробег"** — открывает форму добавления новой записи одометра

**Взаимодействие**:
- Нажать "Добавить пробег" → открывается форма → ввести пробег, дату, опционально заметку → сохранить
- Кликнуть на элемент из "Скоро обслуживание" → переход на страницу элемента
- Кликнуть "Ещё N…" в блоке "Нужно отметить первую замену" → переход на список элементов

**Расчеты**:
- Текущий пробег: `MAX(mileage_km)` из таблицы `odometer_entries`
- Статус элемента: функция `calcServiceStatus()` на основе:
  - Последнего события обслуживания (`lastEvent`)
  - Текущего пробега
  - Интервалов замены (`interval_km`, `interval_days`)
  - Режима измерения (`measurement_mode`: `'km'` или `'calendar'`)
  - Среднего темпа езды (для прогноза дней в режиме `'km'`)

### 2. Список элементов (`/items`)

**Информация**:
- Список всех элементов обслуживания (масло, фильтры и т.д.)
- Для каждого элемента:
  - Название
  - Статус (OVERDUE / SOON / OK)
  - Последняя замена (дата и пробег, если есть)
  - Остаток до следующей замены (км или дни)
- Сортировка: сначала `OVERDUE`, затем `SOON`, затем `OK`, внутри группы — по срочности

**Взаимодействие**:
- Кликнуть на элемент → переход на страницу деталей элемента
- Кнопка "Добавить элемент" → открывается форма создания нового элемента обслуживания

**Расчеты**:
- Аналогично главной странице, используется `calcServiceStatus()` для каждого элемента

### 3. Детали элемента (`/items/[id]`)

**Вкладки**:
- **История** (`?tab=history`): список всех замен элемента (дата, пробег)
- **Расчет** (`?tab=calc`): детальная информация о статусе

**Информация на вкладке "Расчет"**:
- Текущий пробег
- Последняя замена (дата и пробег)
- Интервалы замены (км и/или дни)
- Статус (OVERDUE / SOON / OK / UNKNOWN)
- Остаток до следующей замены (км и дни)
- Прогноз даты замены (если доступен)
- Кнопка "Отметить замену"

**Информация на вкладке "История"**:
- Список всех замен (последняя сверху)
- Для каждой замены: дата и пробег
- Загружается через API (`/api/service-events?itemId=...&limit=10`)

**Взаимодействие**:
- Кнопка "Отметить замену" → открывается форма → ввести дату, пробег, опционально заметку → сохранить
- Кнопка "Настройки" (в шапке) → открывается форма редактирования элемента:
  - Изменить название
  - Изменить интервалы (км и/или дни)
  - Изменить режим измерения (`'km'` или `'calendar'`)
  - Изменить пороги уведомлений (`notify_before_km`, `notify_before_days`)
  - Удалить элемент

**Расчеты**:
- Используется `calcServiceStatus()` с теми же параметрами, что и на главной странице
- Для режима `'km'`: прогноз дней основан на среднем темпе езды (`dailyKmRate`)

### 4. История пробега (`/history`)

**Информация**:
- Список всех записей одометра (последняя сверху)
- Для каждой записи:
  - Пробег (км)
  - Дата и время
  - Прирост пробега (разница с предыдущей записью)
  - Заметка (если есть)

**Взаимодействие**:
- Кнопка "Редактировать последнюю" → открывается форма редактирования последней записи
- Кнопка "Удалить последнюю" → удаляет последнюю запись (по дате `occurred_at`)

**Ограничения**:
- Можно редактировать/удалять только последнюю запись (самую новую по дате)
- При удалении/редактировании проверяется монотонность пробега (пробег не может уменьшаться)

## Основные сущности данных

### 1. Odometer Entry (Запись одометра)

**Таблица**: `odometer_entries`
- `id` (UUID)
- `occurred_at` (TIMESTAMPTZ) — дата записи
- `mileage_km` (INTEGER) — пробег в километрах
- `note` (TEXT, nullable) — заметка
- `created_at` (TIMESTAMPTZ)

**Правила**:
- Пробег должен быть строго больше предыдущего максимального (`MAX(mileage_km)`)
- Проверка на уровне базы данных (триггер `enforce_odometer_monotonic`)

### 2. Service Item (Элемент обслуживания)

**Таблица**: `service_items`
- `id` (UUID)
- `title` (TEXT) — название (например, "Масло двигателя")
- `interval_km` (INTEGER, nullable) — интервал замены по пробегу
- `interval_days` (INTEGER, nullable) — интервал замены по времени
- `measurement_mode` (TEXT: `'km'` или `'calendar'`) — режим измерения
- `notify_before_km` (INTEGER, nullable) — порог уведомления по пробегу
- `notify_before_days` (INTEGER, nullable) — порог уведомления по дням
- `is_active` (BOOLEAN) — активен ли элемент
- `note` (TEXT, nullable)
- `created_at` (TIMESTAMPTZ)

**Правила**:
- Должен быть задан хотя бы один интервал (`interval_km` или `interval_days`)
- Если `measurement_mode === 'km'`: используется только `interval_km`, время игнорируется
- Если `measurement_mode === 'calendar'`: используется только `interval_days`, пробег игнорируется

### 3. Service Event (Событие обслуживания / Замена)

**Таблица**: `service_events`
- `id` (UUID)
- `service_item_id` (UUID) — ссылка на элемент обслуживания
- `occurred_at` (TIMESTAMPTZ) — дата замены
- `mileage_km` (INTEGER) — пробег на момент замены
- `note` (TEXT, nullable) — заметка
- `created_at` (TIMESTAMPTZ)

**Правила**:
- Пробег должен быть не больше текущего максимального пробега
- Пробег может быть меньше текущего (если пользователь отмечает замену задним числом)

## Логика расчетов

### Статус элемента (`calcServiceStatus`)

**Входные данные**:
- `serviceItem` — элемент обслуживания
- `latestOdometerMileageKm` — текущий пробег (максимальный из `odometer_entries`)
- `lastEvent` — последнее событие обслуживания (или `null`)
- `dailyKmRate` — средний темп езды (км/день) для прогноза
- `now` — текущая дата/время

**Выходные данные**:
- `status`: `'OVERDUE'` | `'SOON'` | `'OK'` | `'UNKNOWN'`
- `remainingKm` — остаток до замены по пробегу (или `null`)
- `remainingDays` — остаток до замены по времени (или `null`)
- `limitingFactor` — какой критерий определяет статус (`'km'` | `'time'` | `'none'`)

**Логика**:

1. **Если `lastEvent === null`**: статус `UNKNOWN` (элемент не попадает в "Скоро обслуживание")

2. **Режим `'km'`** (по пробегу):
   - Используется только `interval_km` и `lastEvent.mileage_km`
   - `remainingKm = lastEvent.mileage_km + interval_km - currentMileage`
   - Если `remainingKm <= 0`: статус `OVERDUE`
   - Если `remainingKm > 0` и `remainingDays <= notify_before_days`: статус `SOON`
   - Иначе: статус `OK`
   - `remainingDays` вычисляется как прогноз: `remainingKm / dailyKmRate` (если `dailyKmRate` доступен)

3. **Режим `'calendar'`** (по календарю):
   - Используется только `interval_days` и `lastEvent.occurred_at`
   - `remainingDays = (lastEvent.occurred_at + interval_days) - now`
   - Если `remainingDays <= 0`: статус `OVERDUE`
   - Если `remainingDays > 0` и `remainingDays <= notify_before_days`: статус `SOON`
   - Иначе: статус `OK`
   - `remainingKm` не вычисляется (или `null`)

4. **Выбор "Скоро обслуживание"** (`pickSoonMaintenanceItems`):
   - Элементы со статусом `OVERDUE` — всегда включаются
   - Элементы со статусом `SOON` — включаются
   - Элементы со статусом `OK` — не включаются
   - Элементы со статусом `UNKNOWN` — не включаются
   - Максимум 5 элементов (сортировка по срочности)

### Средний темп езды (`estimateDailyKmRate`)

**Входные данные**: массив записей одометра (последние 50)

**Логика**:
1. Если записей меньше 2: возвращается fallback `30 км/день`
2. Вычисляется средний прирост пробега между соседними записями
3. Вычисляется средний интервал времени между записями
4. `dailyKmRate = средний_прирост_км / средний_интервал_дней`
5. Если результат <= 0 или некорректный: используется fallback `30 км/день`

**Использование**: для прогноза дней до замены в режиме `'km'`

## Взаимосвязи данных

1. **Odometer Entry → Service Event**:
   - При создании события обслуживания проверяется, что `mileage_km <= MAX(odometer_entries.mileage_km)`
   - Текущий пробег используется для расчета статуса элементов

2. **Service Item → Service Event**:
   - Один элемент может иметь много событий (история замен)
   - Последнее событие (`lastEvent`) определяет статус элемента
   - Для режима `'km'`: `lastEvent` выбирается по максимальному `mileage_km`
   - Для режима `'calendar'`: `lastEvent` выбирается по максимальному `occurred_at`

3. **Service Event → Odometer Entry**:
   - Событие содержит `mileage_km`, который должен соответствовать реальному пробегу
   - При расчете статуса используется текущий пробег из `odometer_entries`, а не из события

4. **Расчет статуса**:
   - Зависит от: элемента, последнего события, текущего пробега, среднего темпа езды
   - Обновляется автоматически при изменении любого из этих данных

## Ограничения и особенности

1. **Single-tenant**: приложение рассчитано на одного пользователя и один автомобиль
2. **Монотонность пробега**: пробег не может уменьшаться (проверка на уровне БД)
3. **Редактирование истории**: можно редактировать/удалять только последнюю запись одометра
4. **Режимы измерения**: элемент работает либо по пробегу, либо по календарю (не оба одновременно)
5. **Прогноз дней**: в режиме `'km'` прогноз основан на среднем темпе езды, может быть неточным при малом количестве записей
6. **Fallback темп**: если недостаточно данных для расчета темпа, используется `30 км/день`
