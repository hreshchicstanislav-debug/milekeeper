# UI Status Visual Specification

**Дата создания:** 2025-01-02  
**Тип:** Документ спецификации UI (контракт для реализации)  
**Цель:** Определить визуальные правила и структурные требования для статусного UI на основе выбранной стратегии  
**Область:** Мобильный UI (Home и Items экраны)

**Статус документа:** Complete (All sections defined: Strategy Recap, Signal Hierarchy, Consistency Rules, Home/Items Context Rules, Signal Mapping, Non-Goals, Acceptance Criteria)

---

## 1. Strategy Recap (Short)

**Выбранная стратегия:** Иерархическая мульти-сигнальная стратегия с текстом как первичным сигналом.

**Ключевые принципы:**

- **Primary Signal (обязательный):** Текст статуса передает конкретное значение ("~5 дней", "Просрочено", "Скоро"). Текст является основным носителем информации и должен быть всегда доступен.

- **Secondary Signal (опциональный):** Один визуальный индикатор категории статуса (цвет или символ) поддерживает быстрое распознавание в glance mode. Индикатор всегда вторичен тексту и не дублирует его информацию.

- **Запрещено:** Любые дублирующие сигналы статуса одновременно (например, два цветных акцента, кодирующих один статус). Статус не может кодироваться только цветом без текстового значения.

- **Цель glance mode:** Визуальный индикатор позволяет мгновенно понять категорию (критический/предупреждающий/нормальный) без чтения текста.

- **Цель detail mode:** Текст предоставляет конкретную информацию (количество дней, просрочено/нет) для принятия решений.

- **Адаптация к контексту:** Визуальный вес сигналов адаптируется к контексту (Home: компактнее и спокойнее, Items: детальнее и информативнее), но семантика статусов остается одинаковой.

- **Доступность:** Информация о статусе всегда доступна через текст, независимо от визуального индикатора. Статус не полагается только на цветовое восприятие.

- **Минимизация когнитивной нагрузки:** Один статус = один визуальный сигнал + одно текстовое значение. Отсутствие дублирования и конкуренции между сигналами.

## 2. Visual Signal Hierarchy

### 2.1. Signal Levels

**Primary Signal (обязательный, доминирующий):**

- **Тип:** Текст статуса
- **Роль:** Передача конкретного значения статуса
- **Содержание:** Конкретное значение ("~5 дней", "Просрочено", "Скоро")
- **Требования:**
  - Всегда присутствует
  - Привлекает внимание первым (визуальный приоритет)
  - Читаем и понятен без интерпретации
  - Доступен для screen readers
  - Не зависит от визуального индикатора для понимания

**Secondary Signal (опциональный, поддерживающий):**

- **Тип:** Один визуальный индикатор категории
- **Роль:** Быстрое распознавание категории статуса в glance mode
- **Содержание:** Категория (критический/предупреждающий/нормальный/неизвестный)
- **Требования:**
  - Только один индикатор (не два, не три)
  - Всегда вторичен тексту (не конкурирует за внимание)
  - Не дублирует информацию текста
  - Поддерживает, но не заменяет текст
  - Может быть цветом, символом или другим визуальным паттерном

**Forbidden Signals (запрещены):**

- Любые дублирующие сигналы статуса одновременно
- Статус, кодируемый только цветом без текстового значения
- Множественные визуальные индикаторы одного статуса
- Эмоциональные/тревожные акценты для не-критических статусов
- Визуальные сигналы, конкурирующие с текстом за внимание

### 2.2. Forbidden Combinations

**Запрещенные комбинации сигналов:**

1. **Два цветных акцента для одного статуса:** Запрещено использовать одновременно два цветных элемента (например, левая полоса + цветной прогресс-бар), кодирующих один и тот же статус.

2. **Визуальный индикатор + дублирующий цветной акцент:** Запрещено использовать визуальный индикатор категории вместе с дополнительным цветным акцентом, кодирующим ту же категорию.

3. **Цветной акцент + цветной прогресс-бар с тем же цветом:** Запрещено использовать цветной акцент и цветной прогресс-бар одновременно, если оба кодируют один статус.

4. **Статус только через цвет без текста:** Запрещено кодировать статус только через цвет, символ или другой визуальный элемент без текстового значения.

5. **Эмоциональные акценты для нормальных статусов:** Запрещено использовать тревожные, агрессивные или эмоционально нагруженные визуальные стили для статусов, которые не являются критическими.

6. **Множественные визуальные индикаторы:** Запрещено использовать более одного визуального индикатора категории для одного статуса (например, цвет + символ + форма одновременно).

7. **Конкурирующие сигналы:** Запрещено использовать визуальные сигналы, которые конкурируют с текстом за внимание (например, яркий цветной акцент, который отвлекает от текста).

8. **Относительные индикаторы без конкретных значений:** Запрещено использовать только относительные индикаторы (прогресс-бар, процент) без конкретного текстового значения.

### 2.3. Core Rule: One Status = One Visual Signal + One Text Meaning

**Фундаментальное правило:**

Один статус элемента обслуживания передается через:
- **Один визуальный сигнал** (если используется): кодирует категорию (критический/предупреждающий/нормальный/неизвестный)
- **Одно текстовое значение**: кодирует конкретное значение ("~5 дней", "Просрочено", "Скоро")

**Принципы:**
- Каждый сигнал передает уникальную информацию (категория vs конкретное значение)
- Отсутствие дублирования между сигналами
- Отсутствие дублирования внутри одного типа сигнала (не два визуальных индикатора)
- Текст всегда присутствует и является основным носителем информации

## 3. Consistency Rules (Global)

**Эти правила применяются одинаково на обоих экранах (Home и Items):**

1. **Семантическая консистентность статусов:** Одинаковые статусы (например, "Просрочено", "~5 дней", "Скоро") передаются одинаковыми текстовыми значениями на обоих экранах. Текст статуса не меняется в зависимости от экрана.

2. **Иерархия сигналов:** Текст всегда является первичным сигналом, визуальный индикатор всегда вторичен. Эта иерархия одинакова на обоих экранах.

3. **Обязательность текста:** Текст статуса всегда присутствует и доступен на обоих экранах. Статус не может быть передан только визуальным индикатором.

4. **Единственность визуального индикатора:** Если используется визуальный индикатор категории, он всегда один (не два, не три). Это правило одинаково для обоих экранов.

5. **Запрет дублирования:** Запрещено дублировать информацию о статусе через множественные визуальные сигналы на любом экране. Один статус = один визуальный индикатор (если используется) + один текст.

6. **Доступность через текст:** Информация о статусе всегда доступна через текст, независимо от визуального индикатора. Это правило одинаково для обоих экранов.

7. **Запрет цветовой зависимости:** Статус не может полагаться только на цвет для передачи информации. Текст всегда присутствует как альтернатива. Это правило одинаково для обоих экранов.

8. **Отсутствие визуального шума:** Запрещено создавать избыточный визуальный шум через дублирование сигналов или конкуренцию внимания. Это правило одинаково для обоих экранов.

9. **Запрет агрессивных акцентов по умолчанию:** Запрещено использовать агрессивные, тревожные или эмоционально нагруженные визуальные стили для не-критических статусов на любом экране.

10. **Консистентность базовых паттернов:** Если используется цветовая схема для категорий, она одинакова на обоих экранах. Если используются символы, они одинаковы на обоих экранах. Базовые визуальные паттерны не меняются между экранами.

## 4. Home Screen Rules (Glance Mode)

### 4.1. Screen Purpose and User Behavior

**Назначение экрана:** Dashboard / Overview / Prioritization

**Роль статуса на Home:**
- Быстрый обзор состояния элементов, требующих внимания
- Поддержка принятия решений о приоритетах обслуживания
- Индикация критических и предупреждающих статусов для немедленного реагирования

**Поведение пользователя:**
- Быстрый взгляд на список (1-3 секунды на весь блок)
- Сканирование категорий статусов (критический/предупреждающий/нормальный)
- Приоритизация элементов для дальнейших действий
- Не требует детального чтения каждого элемента

**Временной контекст:**
- Периодические проверки (несколько раз в день или раз в день)
- Краткий просмотр для понимания общего состояния
- Фокус на элементах, требующих внимания

### 4.2. Key Constraints

**Ограничение плотности:**
- До 5 элементов должны помещаться на один мобильный экран без скролла
- Каждый элемент должен занимать минимальное вертикальное пространство
- Отступы между элементами должны быть минимальными, но достаточными для визуального разделения

**Ограничение визуального шума:**
- Визуальный шум должен быть минимален
- Запрещено использовать визуальные элементы, которые создают избыточное визуальное воздействие
- Приоритет — спокойный, контролирующий тон, а не тревожный или агрессивный

**Ограничение информационной плотности:**
- Приоритет — сравнение и приоритизация, не чтение деталей
- Только критическая информация о статусе (категория + минимальное конкретное значение)
- Запрещено добавлять информацию, которая не критична для принятия решений о приоритетах

### 4.3. Text Status Rules (Primary Signal)

**Требования к тексту статуса:**

1. **Краткость и конкретность:** Текст статуса должен быть коротким и конкретным. Минимизировать длину текста при сохранении информативности.

2. **Минимальное конкретное значение:** Текст должен передавать минимально необходимое конкретное значение для приоритизации (например, "~5 дней", "Просрочено", "Скоро").

3. **Читаемость при быстром сканировании:** Текст должен быть читаем при быстром сканировании списка, но не должен доминировать визуально.

4. **Компактность:** Текст должен занимать минимальное горизонтальное пространство, чтобы не требовать переноса строк или обрезки.

5. **Контраст для читаемости:** Контраст текста должен быть достаточным для читаемости, но не избыточным (не должен привлекать внимание сильнее, чем необходимо).

### 4.4. Visual Indicator Rules (Secondary Signal)

**Требования к визуальному индикатору:**

1. **Максимально легкий визуальный вес:** Вторичный визуальный индикатор должен быть максимально легким визуально. Минимизировать заметность индикатора при сохранении распознаваемости.

2. **Поддержка glance mode:** Индикатор должен поддерживать быстрое распознавание категории (критический/предупреждающий/нормальный) без чтения текста.

3. **Отсутствие доминирования:** Индикатор не должен доминировать над текстом или конкурировать с ним за внимание. Индикатор всегда вторичен.

4. **Снижение эмоционального воздействия:** Для критических статусов индикатор должен быть менее агрессивным, менее тревожным, чем на Items. Поддержка спокойного тона.

5. **Минимальное использование пространства:** Индикатор должен занимать минимальное пространство (вертикальное и горизонтальное).

### 4.5. Layout and Spacing Constraints

**Запрещенные элементы:**

1. **Элементы, увеличивающие высоту строки:** Запрещено использовать визуальные элементы, которые увеличивают высоту строки элемента (например, прогресс-бары, дополнительные строки текста, декоративные элементы).

2. **Дополнительные визуальные акценты:** Запрещено добавлять дополнительные визуальные акценты, которые не несут критической информации (например, декоративные рамки, тени, градиенты).

3. **Элементы, требующие дополнительного пространства:** Запрещено использовать элементы, которые требуют дополнительного вертикального или горизонтального пространства сверх минимально необходимого.

**Требования к компактности:**

1. **Минимальные отступы:** Отступы между элементами должны быть минимальными, но достаточными для визуального разделения и читаемости.

2. **Оптимизация вертикального пространства:** Каждый элемент должен занимать минимальное вертикальное пространство, необходимое для размещения текста статуса и визуального индикатора.

3. **Отсутствие избыточных разделителей:** Разделители между элементами должны быть минимальными и не занимать дополнительное пространство.

### 4.6. Priority Rules

**Приоритеты для Home:**

1. **Приоритет 1: Компактность:** Обеспечить размещение 5 элементов без скролла — это критическое требование.

2. **Приоритет 2: Быстрое распознавание категории:** Визуальный индикатор должен позволять быстро определить категорию статуса.

3. **Приоритет 3: Конкретное значение:** Текст должен предоставлять минимально необходимое конкретное значение для приоритизации.

4. **Приоритет 4: Спокойный тон:** Эмоциональный тон должен быть спокойным, контролирующим, не тревожным.

## 5. Items Screen Rules (Detail Mode)

### 5.1. Screen Purpose and User Behavior

**Назначение экрана:** Inspection / Comparison / Exploration

**Роль статуса на Items:**
- Детальный осмотр всех элементов обслуживания
- Сравнение статусов между элементами
- Полное понимание состояния каждого элемента

**Поведение пользователя:**
- Осознанный просмотр списка всех элементов
- Детальное изучение статуса каждого элемента
- Сравнение статусов для понимания относительной важности
- Готовность потратить больше времени на анализ

**Временной контекст:**
- Менее частые проверки (раз в несколько дней или раз в неделю)
- Более длительный просмотр (1-3 минуты на весь список)
- Требует более детального изучения каждого элемента

### 5.2. Differences from Home

**Допустимые отличия от Home:**

1. **Более высокий визуальный вес:** Допускается более высокий визуальный вес сигналов (текста и визуального индикатора) для улучшения читаемости и информативности.

2. **Большая плотность информации:** Допускается большая информационная плотность, если это улучшает понимание статуса элемента.

3. **Более заметный визуальный индикатор:** Визуальный индикатор может быть более заметным, чем на Home, для поддержки сравнения между элементами.

4. **Более комфортные отступы:** Допускаются более комфортные отступы между элементами для удобства детального изучения.

5. **Скролл допустим:** Скролл допустим для размещения всех элементов, так как Items предназначен для детального просмотра.

**Недопустимые отличия от Home:**

1. **Семантика статусов:** Семантика статусов (текстовые значения, категории) должна быть одинаковой на обоих экранах.

2. **Иерархия сигналов:** Иерархия сигналов (текст первичный, индикатор вторичный) должна быть одинаковой на обоих экранах.

3. **Количество индикаторов:** Количество визуальных индикаторов должно быть одинаковым (один индикатор, не два).

### 5.3. Text Status Rules (Primary Signal)

**Требования к тексту статуса:**

1. **Первичность текста:** Текст статуса остается первичным сигналом и должен привлекать внимание первым.

2. **Читаемость для детального изучения:** Текст должен быть оптимизирован для детального чтения, а не только для быстрого сканирования.

3. **Полное конкретное значение:** Текст должен предоставлять полное конкретное значение статуса для принятия обоснованных решений.

4. **Контраст для читаемости:** Контраст текста должен быть достаточным для комфортного детального чтения.

5. **Достаточный размер:** Размер текста должен быть достаточным для читаемости при детальном изучении, но не избыточным.

### 5.4. Visual Indicator Rules (Secondary Signal)

**Требования к визуальному индикатору:**

1. **Заметность для сравнения:** Визуальный индикатор может быть более заметным, чем на Home, для поддержки сравнения статусов между элементами.

2. **Информативность:** Индикатор должен быть достаточно информативным для поддержки детального анализа, но не должен доминировать над текстом.

3. **Вторичная роль:** Индикатор остается вторичным сигналом и не должен конкурировать с текстом за внимание.

4. **Запрет второго индикатора:** Запрещено добавлять второй визуальный индикатор статуса (например, дополнительный цветной акцент, прогресс-бар, символ). Один статус = один визуальный индикатор.

5. **Поддержка сравнения:** Индикатор должен поддерживать сравнение статусов между элементами, но не должен быть единственным способом сравнения (текст также должен поддерживать сравнение).

### 5.5. Information Density Rules

**Допустимая плотность информации:**

1. **Полная информация:** Допускается отображение полной информации о статусе (категория через индикатор + конкретное значение через текст).

2. **Комфортные отступы:** Допускаются более комфортные отступы между элементами для удобства детального изучения.

3. **Читаемость приоритетнее компактности:** Читаемость и информативность имеют приоритет над компактностью на Items.

**Запрещенные элементы:**

1. **Второй индикатор статуса:** Запрещено добавлять второй визуальный индикатор статуса (например, прогресс-бар, дополнительный цветной акцент, символ).

2. **Дублирующие сигналы:** Запрещено дублировать информацию о статусе через множественные визуальные сигналы.

3. **Избыточные декоративные элементы:** Запрещено добавлять декоративные элементы, которые не несут информации о статусе.

### 5.6. Priority Rules

**Приоритеты для Items:**

1. **Приоритет 1: Информативность:** Обеспечить полную информацию о статусе для детального изучения.

2. **Приоритет 2: Читаемость:** Обеспечить комфортную читаемость текста статуса для детального анализа.

3. **Приоритет 3: Сравнение:** Поддержать сравнение статусов между элементами через текст и визуальный индикатор.

4. **Приоритет 4: Консистентность:** Сохранить консистентность семантики статусов с Home экраном.

## 6. Signal-to-Meaning Mapping

### 6.1. Mapping Rules

**Фундаментальные правила маппинга:**

1. **Текст всегда передает конкретное значение:** Текстовое значение должно быть конкретным и однозначным. Текст не может быть абстрактным или требующим интерпретации.

2. **Визуальный индикатор только категория:** Визуальный индикатор может кодировать только категорию статуса (критический/предупреждающий/нормальный/неизвестный), никогда не конкретное значение.

3. **Визуальный индикатор не противоречит тексту:** Визуальный индикатор не может противоречить текстовому значению. Если текст говорит "Просрочено", индикатор должен кодировать критическую категорию, а не нормальную.

4. **Один статус = одна семантика:** Один статус элемента (например, OVERDUE) всегда передается одинаковой семантикой на обоих экранах (одинаковый текст, одинаковая категория индикатора).

### 6.2. Status-to-Signal Mapping Table

| Status Meaning (Semantic) | Required Text Meaning | Visual Role (Secondary Signal) | Constraints |
|---------------------------|----------------------|--------------------------------|-------------|
| **OVERDUE** (Просрочено) | Текст должен явно указывать на просрочку: "Просрочено" | Может кодировать только критическую категорию | Визуальный индикатор не может кодировать нормальную или предупреждающую категорию |
| **SOON** (Скоро, надежный прогноз) | Текст должен передавать конкретное количество дней: "~N дней" (N — округленное до целого число) | Может кодировать предупреждающую категорию | Визуальный индикатор не может кодировать критическую категорию, если текст не указывает на просрочку |
| **SOON** (Скоро, ненадежный прогноз) | Текст должен передавать неопределенность: "Скоро" (без конкретного количества дней) | Может кодировать предупреждающую или неизвестную категорию | Визуальный индикатор должен отражать ненадежность прогноза |
| **OK** (Нормальный) | Текст должен передавать нормальное состояние: "~N дней" (где N достаточно большое) или отсутствие текста статуса | Может кодировать нормальную категорию | Визуальный индикатор не может кодировать критическую или предупреждающую категорию |
| **UNKNOWN** (Неизвестный) | Текст должен передавать неопределенность: "Скоро" или отсутствие конкретного значения | Может кодировать неизвестную или предупреждающую категорию | Визуальный индикатор должен отражать неопределенность статуса |

### 6.3. Text Meaning Requirements

**Правила для текстовых значений:**

1. **Конкретность:** Текст должен быть конкретным и однозначным. Запрещено использовать абстрактные или неоднозначные формулировки.

2. **Обязательность для критических статусов:** Для статуса OVERDUE текст "Просрочено" обязателен. Не допускается использование только визуального индикатора.

3. **Формат для прогнозов:** Для надежных прогнозов текст должен быть в формате "~N дней", где N — округленное до целого число дней. Запрещено использовать только относительные значения без конкретного числа.

4. **Формат для ненадежных прогнозов:** Для ненадежных прогнозов текст "Скоро" допустим, но должен сопровождаться индикацией ненадежности (например, через визуальный индикатор или дополнительный символ).

5. **Отсутствие противоречий:** Текст не может противоречить визуальному индикатору. Если текст говорит "Просрочено", индикатор не может кодировать нормальную категорию.

### 6.4. Visual Role Requirements

**Правила для визуального индикатора:**

1. **Только категория:** Визуальный индикатор может кодировать только категорию статуса (критический/предупреждающий/нормальный/неизвестный), никогда не конкретное значение (количество дней, просрочено/нет).

2. **Запрет кодирования конкретных значений:** Запрещено использовать визуальный индикатор для передачи конкретных значений (например, "5 дней", "1000 км", "просрочено на 3 дня").

3. **Согласованность с текстом:** Визуальный индикатор должен быть согласован с текстом. Если текст указывает на критический статус, индикатор должен кодировать критическую категорию.

4. **Поддержка glance mode:** Индикатор должен поддерживать быстрое распознавание категории без чтения текста, но не должен заменять текст.

5. **Отсутствие противоречий:** Индикатор не может противоречить тексту. Если текст говорит "~30 дней" (нормальный статус), индикатор не может кодировать критическую категорию.

### 6.5. Cross-Screen Consistency

**Правила консистентности между экранами:**

1. **Одинаковый текст для одинаковых статусов:** Если элемент имеет статус OVERDUE на Home, текст "Просрочено" должен быть одинаковым на Items.

2. **Одинаковая категория индикатора:** Если элемент имеет критический статус на Home, визуальный индикатор должен кодировать критическую категорию и на Items.

3. **Одинаковая семантика:** Семантика статуса (OVERDUE, SOON, OK, UNKNOWN) не меняется между экранами. Только визуальный вес сигналов может адаптироваться.

## 7. Non-Goals

**Этот UI статусов НЕ предназначен для:**

### 7.1. Decorative Signaling

- **Нет декоративных элементов:** UI не должен включать декоративные визуальные элементы, которые не несут информации о статусе (например, декоративные рамки, тени, градиенты, анимации).

- **Нет визуального "украшения":** Статус не должен быть визуально "украшен" для эстетических целей. Каждый визуальный элемент должен нести функциональную информацию.

- **Нет избыточных визуальных эффектов:** Запрещено использовать визуальные эффекты (например, пульсация, мигание, анимация), которые не несут информации о статусе.

### 7.2. Emotional or Anxiety-Inducing Design

- **Нет эмоциональной манипуляции:** UI не должен использовать эмоциональные или тревожные визуальные стили для манипуляции поведением пользователя или создания чувства срочности там, где его нет.

- **Нет агрессивных акцентов для не-критических статусов:** Запрещено использовать агрессивные, тревожные или эмоционально нагруженные визуальные стили для статусов, которые не являются критическими.

- **Нет создания тревоги:** UI не должен создавать избыточную тревогу или стресс через визуальные сигналы. Эмоциональный тон должен быть спокойным и контролирующим, особенно на Home.

### 7.3. Gamification or Reward Mechanics

- **Нет игровых элементов:** UI не должен включать игровые элементы (например, бейджи, уровни, достижения, прогресс-бары как награда).

- **Нет мотивационных сигналов:** Статус не должен использоваться для мотивации пользователя через визуальные награды или поощрения.

- **Нет соревновательных элементов:** UI не должен создавать ощущение соревнования или игры через визуальные сигналы статуса.

### 7.4. Redundancy of Status Signals

- **Нет дублирования сигналов:** UI не должен дублировать информацию о статусе через множественные визуальные сигналы (например, два цветных акцента, цвет + символ + форма для одного статуса).

- **Нет избыточных способов передачи одного статуса:** Запрещено использовать более одного способа передачи одной и той же информации о статусе (например, цвет + прогресс-бар + символ для одной категории).

- **Нет повторения информации:** Визуальные сигналы не должны повторять информацию, уже переданную текстом, или наоборот.

### 7.5. Optimization for Marketing or Engagement

- **Нет маркетинговых целей:** UI не должен оптимизироваться для маркетинговых целей (например, привлечение внимания, увеличение времени в приложении, создание ощущения активности).

- **Нет оптимизации для вовлеченности:** Статус не должен использоваться для увеличения вовлеченности пользователя через визуальные стимулы или призывы к действию.

- **Нет создания ложной срочности:** UI не должен создавать ложное ощущение срочности через визуальные сигналы для увеличения использования приложения.

### 7.6. Visual Complexity or Showcase

- **Нет демонстрации визуальных возможностей:** UI не должен демонстрировать визуальные возможности или сложность дизайна. Простота и ясность имеют приоритет.

- **Нет избыточной визуальной сложности:** Запрещено создавать избыточную визуальную сложность для демонстрации дизайнерских навыков или технологических возможностей.

- **Нет визуального "шоу":** Статус не должен быть визуальным "шоу". Функциональность и ясность имеют приоритет над визуальной демонстрацией.

### 7.7. Status as Primary Visual Element

- **Нет доминирования статуса:** Статус не должен доминировать визуально над другими элементами интерфейса (например, название элемента, другие метаданные).

- **Нет статуса как декорации:** Статус не должен использоваться как декоративный элемент для улучшения внешнего вида интерфейса.

- **Нет статуса как брендинга:** Статус не должен использоваться для брендинга или создания визуальной идентичности приложения.

## 8. Acceptance Criteria

### 8.1. Glance Mode Success

**Критерий:** Пользователь может определить наиболее критичный элемент и ранжировать срочность без чтения деталей.

**Pass Criteria:**

1. **Время до идентификации критичного элемента:** Пользователь может определить наиболее критичный элемент (OVERDUE или наиболее срочный SOON) в списке из 5 элементов за время ≤ 2 секунд.

2. **Ранжирование без чтения:** Пользователь может ранжировать элементы по срочности (от наиболее критичного к наименее критичному) без чтения текстовых значений статусов, используя только визуальный индикатор.

3. **Распознавание категории:** Пользователь может правильно определить категорию статуса (критический/предупреждающий/нормальный) для каждого элемента за время ≤ 1 секунды на элемент при быстром сканировании.

4. **Отсутствие необходимости возврата:** Пользователь не должен возвращаться к элементам для повторного просмотра после первого сканирования для понимания категории статуса.

**Fail Criteria:**

- Пользователь не может определить наиболее критичный элемент за 2 секунды
- Пользователь не может ранжировать элементы по срочности без чтения текста
- Пользователь должен возвращаться к элементам для повторного просмотра
- Визуальный индикатор не распознается или неоднозначен

### 8.2. Density Success

**Критерий:** На Home экране все 5 элементов видны без скролла на стандартном мобильном устройстве.

**Pass Criteria:**

1. **Видимость всех элементов:** Все 5 элементов блока "Скоро обслуживание" полностью видны на экране без необходимости скролла на стандартных мобильных устройствах (ширина экрана 375-430px, высота экрана стандартная для мобильных устройств).

2. **Отсутствие обрезки:** Ни один элемент не обрезан и не частично виден. Все элементы полностью видны от начала до конца.

3. **Читаемость:** Все текстовые значения статусов читаемы и не обрезаны. Текст не требует горизонтального скролла или обрезки.

4. **Визуальные индикаторы видны:** Все визуальные индикаторы (если используются) полностью видны и не обрезаны.

**Fail Criteria:**

- Требуется скролл для просмотра всех 5 элементов
- Элементы обрезаны или частично видны
- Текст обрезан или требует горизонтального скролла
- Визуальные индикаторы обрезаны или не видны

### 8.3. Consistency Success

**Критерий:** Одинаковые статусы передаются одинаковыми сигналами на обоих экранах.

**Pass Criteria:**

1. **Одинаковый текст:** Если элемент имеет статус OVERDUE на Home, текст "Просрочено" должен быть идентичным на Items. Если элемент имеет статус SOON с "~5 дней" на Home, тот же текст "~5 дней" должен быть на Items.

2. **Одинаковая категория индикатора:** Если элемент имеет критический статус на Home, визуальный индикатор должен кодировать критическую категорию и на Items. Категория индикатора не меняется между экранами.

3. **Отсутствие дополнительных сигналов:** На Items не должно появляться дополнительных визуальных сигналов статуса, которых нет на Home (например, второй цветной акцент, дополнительный символ, прогресс-бар).

4. **Семантическая консистентность:** Семантика статуса (OVERDUE, SOON, OK, UNKNOWN) не меняется между экранами. Одинаковый статус = одинаковые сигналы.

**Fail Criteria:**

- Текст статуса отличается между Home и Items для одного и того же элемента
- Категория визуального индикатора отличается между Home и Items для одного и того же статуса
- На Items появляются дополнительные визуальные сигналы статуса, которых нет на Home
- Семантика статуса интерпретируется по-разному на разных экранах

### 8.4. Accessibility Success

**Критерий:** Статус полностью понятен без зависимости от цветового восприятия.

**Pass Criteria:**

1. **Понимание без цвета:** Пользователь с дальтонизмом или нарушением цветового восприятия может полностью понять статус элемента, используя только текст. Текст предоставляет всю необходимую информацию о статусе.

2. **Текст как альтернатива:** Текст статуса является полной альтернативой визуальному индикатору. Если визуальный индикатор недоступен или не распознается, текст предоставляет всю информацию.

3. **Отсутствие цветовой зависимости:** Статус не кодируется только цветом. Цвет (если используется) всегда сопровождается текстом, который передает ту же информацию.

4. **Screen reader доступность:** Текст статуса доступен для screen readers и содержит всю информацию о статусе.

**Fail Criteria:**

- Пользователь с дальтонизмом не может понять статус без чтения текста
- Текст не предоставляет полной альтернативы визуальному индикатору
- Статус кодируется только цветом без текстовой альтернативы
- Текст недоступен для screen readers или не содержит полной информации

### 8.5. Cognitive Load Success

**Критерий:** Статус не создает избыточной когнитивной нагрузки через дублирование сигналов или конкуренцию внимания.

**Pass Criteria:**

1. **Отсутствие дублирования:** Один статус передается через один визуальный индикатор (если используется) + один текст. Отсутствие дублирования информации между сигналами.

2. **Отсутствие конкуренции:** Визуальный индикатор не конкурирует с текстом за внимание. Текст привлекает внимание первым, индикатор — вторым.

3. **Четкая иерархия:** Иерархия сигналов четкая и понятная. Пользователь не испытывает необходимости "расшифровывать" статус или выбирать между конкурирующими сигналами.

4. **Минимальная когнитивная нагрузка:** Пользователь может понять статус без дополнительных вычислений или интерпретаций. Информация передается прямо и однозначно.

**Fail Criteria:**

- Один статус передается через множественные визуальные индикаторы (два, три или более)
- Визуальный индикатор конкурирует с текстом за внимание
- Иерархия сигналов неясна или требует интерпретации
- Пользователь должен "расшифровывать" статус или выбирать между конкурирующими сигналами

### 8.6. Text Clarity Success

**Критерий:** Текст статуса однозначен и не требует интерпретации.

**Pass Criteria:**

1. **Конкретность текста:** Текст статуса конкретен и однозначен. "Просрочено" означает просрочку, "~5 дней" означает приблизительно 5 дней, "Скоро" означает неопределенность.

2. **Отсутствие абстракций:** Текст не использует абстрактные или неоднозначные формулировки, требующие интерпретации.

3. **Читаемость:** Текст читаем и понятен без дополнительного контекста или обучения.

4. **Отсутствие противоречий:** Текст не противоречит визуальному индикатору. Если текст говорит "Просрочено", индикатор не может кодировать нормальную категорию.

**Fail Criteria:**

- Текст неоднозначен или требует интерпретации
- Текст использует абстрактные формулировки
- Текст противоречит визуальному индикатору
- Текст требует дополнительного контекста для понимания

### 8.7. Visual Indicator Clarity Success

**Критерий:** Визуальный индикатор (если используется) однозначно кодирует категорию статуса.

**Pass Criteria:**

1. **Однозначность категории:** Визуальный индикатор однозначно кодирует категорию (критический/предупреждающий/нормальный/неизвестный). Пользователь может определить категорию без чтения текста.

2. **Отсутствие кодирования конкретных значений:** Визуальный индикатор не кодирует конкретные значения (количество дней, просрочено/нет). Индикатор кодирует только категорию.

3. **Согласованность с текстом:** Визуальный индикатор согласован с текстом. Если текст указывает на критический статус, индикатор кодирует критическую категорию.

4. **Распознаваемость:** Визуальный индикатор распознаваем и понятен без обучения или дополнительного контекста.

**Fail Criteria:**

- Визуальный индикатор неоднозначен или требует интерпретации
- Визуальный индикатор кодирует конкретные значения вместо категории
- Визуальный индикатор противоречит тексту
- Визуальный индикатор требует обучения для понимания

## 9. Priority & Urgency Model

### 9.1. What is Urgency?

**Определение срочности в контексте элементов обслуживания:**

Срочность — это мера того, насколько быстро элемент обслуживания требует внимания пользователя. Срочность определяется двумя факторами:

1. **Семантическая срочность (категория статуса):** Категория статуса (OVERDUE, SOON, OK, UNKNOWN) определяет общий уровень срочности элемента.

2. **Числовая срочность (количество дней):** Конкретное количество оставшихся дней до следующего обслуживания определяет относительную срочность внутри категории.

**Связь между семантической и числовой срочностью:**

- Семантическая срочность определяет приоритет категории (OVERDUE > SOON > OK > UNKNOWN)
- Числовая срочность определяет порядок внутри категории (меньше дней = более срочно)
- Оба фактора используются для сортировки элементов

### 9.2. Semantic Urgency vs Numeric Urgency

**Семантическая срочность (категория статуса):**

- **OVERDUE:** Критическая срочность — элемент просрочен и требует немедленного внимания
- **SOON:** Предупреждающая срочность — элемент требует внимания в ближайшее время
- **OK:** Нормальная срочность — элемент в порядке, не требует немедленного внимания
- **UNKNOWN:** Неопределенная срочность — недостаточно данных для определения статуса

**Числовая срочность (количество дней):**

- Для OVERDUE: более отрицательные значения (более просроченные) = более срочно
- Для SOON: меньшее количество дней = более срочно
- Для OK: меньшее количество дней = более срочно (но все еще нормальный статус)
- Для UNKNOWN: числовая срочность недоступна

**Приоритет сортировки:**

Семантическая срочность имеет приоритет над числовой. Элемент с OVERDUE всегда выше элемента с SOON, независимо от количества дней.

### 9.3. Why Urgency Ordering is Critical for Home

**Роль сортировки по срочности на Home:**

1. **Glance Mode Support:** Пользователь должен видеть наиболее критичные элементы первыми при быстром взгляде. Сортировка по срочности обеспечивает это.

2. **Приоритизация:** Пользователь принимает решения о приоритетах обслуживания. Сортировка по срочности помогает определить, что делать в первую очередь.

3. **Эффективность:** Пользователь не должен просматривать весь список для поиска критичных элементов. Наиболее срочные элементы должны быть наверху.

4. **Ограничение видимости:** На Home показывается только до 5 элементов. Сортировка по срочности гарантирует, что наиболее критичные элементы видны первыми.

## 10. Sorting Rules (Global)

### 10.1. Primary Sorting Key: Urgency Category

**Правило:** Элементы сортируются сначала по категории срочности (семантическая срочность).

**Порядок категорий (от наиболее срочной к наименее срочной):**

1. **OVERDUE** (наиболее срочная)
2. **SOON** (предупреждающая)
3. **OK** (нормальная)
4. **UNKNOWN** (наименее срочная, неопределенная)

**Принцип:** Элемент с более высокой категорией срочности всегда выше элемента с более низкой категорией, независимо от числовых значений.

### 10.2. Secondary Sorting Key: Numeric Remaining Days (Ascending)

**Правило:** Внутри одной категории элементы сортируются по количеству оставшихся дней (по возрастанию — меньше дней = выше).

**Для OVERDUE:**

- Сортировка по "степени просрочки" (более отрицательные значения = более срочно)
- Элемент, просроченный на 10 дней, выше элемента, просроченного на 5 дней
- Используется минимальное значение из remainingDays и remainingKm (если доступны оба)

**Для SOON:**

- Сортировка по remainingDays (меньше дней = выше)
- Элемент с "~3 дня" выше элемента с "~7 дней"
- Элементы с надежным прогнозом (конкретное количество дней) выше элементов с ненадежным прогнозом ("Скоро")

**Для OK:**

- Сортировка по remainingDays (меньше дней = выше)
- Элемент с "~30 дней" выше элемента с "~60 дней"

**Для UNKNOWN:**

- Числовая сортировка недоступна (нет данных)
- Используется третичный ключ сортировки

### 10.3. Tertiary Sorting Key: Fallback and Unknown Handling

**Правило:** Для разрешения ничьих используется третичный ключ сортировки.

**Порядок применения третичных ключей:**

1. **RemainingKm (если доступно):** Для элементов с одинаковой категорией и одинаковым remainingDays, сортировка по remainingKm (меньше км = выше)

2. **Наличие данных:** Элементы с данными (remainingDays или remainingKm) выше элементов без данных

3. **Название элемента (алфавитный порядок):** Для полного разрешения ничьих используется алфавитная сортировка по названию элемента (для стабильности сортировки)

### 10.4. Explicit Ordering Rules

**Строгий порядок сортировки:**

1. **OVERDUE (most overdue first):**
   - Все элементы OVERDUE выше всех элементов SOON/OK/UNKNOWN
   - Внутри OVERDUE: более просроченные (более отрицательные значения) выше менее просроченных
   - При равной степени просрочки: по remainingKm (если доступно), затем по названию

2. **SOON (reliable, fewer days first):**
   - Все элементы SOON выше всех элементов OK/UNKNOWN
   - Внутри SOON: элементы с надежным прогнозом (конкретное количество дней) выше элементов с ненадежным прогнозом ("Скоро")
   - Внутри надежных SOON: меньшее количество дней выше большего
   - При равном количестве дней: по remainingKm (если доступно), затем по названию

3. **SOON (unreliable / unknown):**
   - Элементы SOON с ненадежным прогнозом ("Скоро") ниже элементов SOON с надежным прогнозом
   - Внутри ненадежных SOON: по remainingKm (если доступно), затем по названию

4. **OK (least urgent):**
   - Все элементы OK выше всех элементов UNKNOWN
   - Внутри OK: меньшее количество дней выше большего
   - При равном количестве дней: по remainingKm (если доступно), затем по названию

5. **UNKNOWN (no data):**
   - Все элементы UNKNOWN в конце списка
   - Внутри UNKNOWN: по названию (алфавитный порядок)

## 11. Home-Specific Ordering Rules

### 11.1. Urgency-Based Sorting Requirement

**Правило:** Элементы на Home должны быть отсортированы по срочности по убыванию (наиболее срочные сверху).

**Требования:**

1. **Строгое убывание срочности:** Срочность строго убывает сверху вниз. Элемент с более высокой срочностью всегда выше элемента с более низкой срочностью.

2. **Визуальная согласованность:** Визуальное представление (текст и индикатор) должно соответствовать порядку сортировки. Наиболее критичный элемент визуально наверху.

3. **Отсутствие инверсий:** Запрещено, чтобы элемент с более низкой срочностью визуально появлялся выше элемента с более высокой срочностью.

### 11.2. Maximum Items Limit

**Правило:** На Home показывается максимум 5 элементов.

**Требования:**

1. **Жесткий лимит:** Максимум 5 элементов в блоке "Скоро обслуживание". Если элементов больше 5, показываются только 5 наиболее срочных.

2. **Отбор по срочности:** Если существует более 5 элементов, требующих внимания, отбираются только 5 наиболее срочных согласно правилам сортировки.

3. **Отсутствие обрезки:** Все 5 элементов должны быть полностью видны без скролла. Элементы не должны быть обрезаны или частично видны.

### 11.3. Selection Logic for Home

**Правило отбора элементов для Home:**

1. **Приоритет OVERDUE:** Все элементы OVERDUE включаются в список (если их ≤ 5).

2. **Приоритет SOON:** Если элементов OVERDUE < 5, включаются элементы SOON по срочности до достижения лимита 5.

3. **Приоритет OK:** Элементы OK включаются только если элементов OVERDUE + SOON < 5. OK элементы показываются только если есть свободные места.

4. **Исключение UNKNOWN:** Элементы UNKNOWN не показываются на Home (недостаточно данных для принятия решений).

**Результат:** Список на Home содержит только элементы OVERDUE, SOON и (опционально) OK, отсортированные по срочности, максимум 5 элементов.

### 11.4. Bottom Element Rule

**Правило:** Наименее срочный из показанных элементов всегда внизу списка.

**Требования:**

1. **Визуальная согласованность:** Если показано 5 элементов, 5-й элемент (наименее срочный) всегда внизу.

2. **Предсказуемость:** Пользователь может ожидать, что наименее срочный элемент всегда внизу списка.

3. **Отсутствие OK выше SOON:** Если показаны элементы OK, они всегда ниже всех элементов SOON и OVERDUE.

### 11.5. OK Items Visibility Rule

**Правило:** Элементы OK показываются только если есть свободные места (меньше 5 элементов OVERDUE + SOON).

**Требования:**

1. **Приоритет критичных элементов:** Элементы OVERDUE и SOON имеют приоритет над элементами OK.

2. **Ограниченная видимость OK:** Элементы OK показываются только если элементов OVERDUE + SOON < 5.

3. **Отсутствие OK при переполнении:** Если элементов OVERDUE + SOON ≥ 5, элементы OK не показываются на Home.

## 12. Items Screen Ordering Rules

### 12.1. Same Urgency Ordering Logic

**Правило:** На Items используется та же логика сортировки по срочности, что и на Home.

**Требования:**

1. **Идентичная логика сортировки:** Порядок сортировки (OVERDUE > SOON > OK > UNKNOWN, затем по remainingDays) идентичен на обоих экранах.

2. **Консистентность:** Элемент, который выше другого элемента на Home, должен быть выше и на Items (если оба элемента присутствуют на обоих экранах).

3. **Предсказуемость:** Пользователь может ожидать одинакового порядка элементов на обоих экранах.

### 12.2. No Hard Limit on Items

**Правило:** На Items нет жесткого лимита на количество элементов.

**Требования:**

1. **Все элементы видны:** Все элементы обслуживания показываются на Items, независимо от их количества.

2. **Скролл допустим:** Скролл допустим для просмотра всех элементов, так как Items предназначен для детального изучения.

3. **Отсутствие обрезки:** Элементы не должны быть обрезаны или частично видны из-за лимита.

### 12.3. Stable and Predictable Ordering

**Правило:** Сортировка на Items должна быть стабильной и предсказуемой.

**Требования:**

1. **Стабильность:** Порядок элементов не меняется при повторных загрузках, если данные не изменились.

2. **Предсказуемость:** Пользователь может предсказать, где находится элемент в списке, основываясь на его статусе и количестве дней.

3. **Отсутствие случайности:** Порядок не зависит от случайных факторов или порядка загрузки данных.

4. **Tie-breaker:** Для элементов с одинаковой срочностью используется стабильный tie-breaker (например, алфавитный порядок по названию).

### 12.4. Visual Scan Support

**Правило:** Пользователь должен иметь возможность визуально сканировать список от наиболее критичного к наименее критичному.

**Требования:**

1. **Визуальная согласованность:** Визуальное представление (текст и индикатор) должно соответствовать порядку сортировки. Наиболее критичные элементы визуально наверху.

2. **Отсутствие инверсий:** Запрещено, чтобы элемент с более низкой срочностью визуально появлялся выше элемента с более высокой срочностью.

3. **Поддержка сравнения:** Пользователь должен иметь возможность сравнивать срочность элементов, просматривая список сверху вниз.

## 13. Edge Cases & Tie-Breaking

### 13.1. Two OVERDUE Items with Different Overdue Duration

**Сценарий:** Два элемента имеют статус OVERDUE, но с разной степенью просрочки.

**Правило сортировки:**

1. **Приоритет более просроченного:** Элемент, просроченный на большее количество дней, выше элемента, просроченного на меньшее количество дней.

2. **Использование минимального значения:** Если доступны и remainingDays, и remainingKm, используется минимальное (наиболее отрицательное) значение для определения степени просрочки.

3. **Пример:** Элемент, просроченный на 10 дней, выше элемента, просроченного на 5 дней.

**Tie-breaking:**

- Если степень просрочки одинакова (одинаковые remainingDays), используется remainingKm (если доступно)
- Если и remainingDays, и remainingKm одинаковы, используется алфавитный порядок по названию

### 13.2. Two SOON Items with Equal Remaining Days

**Сценарий:** Два элемента имеют статус SOON с одинаковым количеством оставшихся дней.

**Правило сортировки:**

1. **Приоритет надежного прогноза:** Элемент с надежным прогнозом (конкретное количество дней) выше элемента с ненадежным прогнозом ("Скоро").

2. **При равной надежности:** Если оба элемента имеют надежный прогноз с одинаковым количеством дней, используется remainingKm (если доступно).

3. **Пример:** Элемент с "~5 дней" (надежный) выше элемента с "Скоро" (ненадежный), даже если оба имеют статус SOON.

**Tie-breaking:**

- Если оба элемента имеют надежный прогноз с одинаковым remainingDays, используется remainingKm (если доступно)
- Если remainingKm одинаково или недоступно, используется алфавитный порядок по названию

### 13.3. Items with Unknown or Unreliable Prediction

**Сценарий:** Элементы с неизвестным или ненадежным прогнозом (UNKNOWN или SOON с "Скоро").

**Правило сортировки для UNKNOWN:**

1. **Позиция в списке:** Элементы UNKNOWN всегда в конце списка, после всех элементов OVERDUE, SOON и OK.

2. **Внутри UNKNOWN:** Элементы UNKNOWN сортируются по алфавитному порядку названий.

3. **Отсутствие на Home:** Элементы UNKNOWN не показываются на Home (недостаточно данных для принятия решений).

**Правило сортировки для SOON с ненадежным прогнозом:**

1. **Позиция в списке:** Элементы SOON с ненадежным прогнозом ("Скоро") ниже элементов SOON с надежным прогнозом ("~N дней").

2. **Внутри ненадежных SOON:** Элементы сортируются по remainingKm (если доступно), затем по названию.

3. **Видимость на Home:** Элементы SOON с ненадежным прогнозом могут показываться на Home, если есть свободные места и они более срочные, чем элементы OK.

### 13.4. Items Without Last Event

**Сценарий:** Элементы без истории замен (lastEvent === null).

**Правило сортировки:**

1. **Статус UNKNOWN:** Элементы без lastEvent имеют статус UNKNOWN.

2. **Позиция в списке:** Элементы без lastEvent всегда в конце списка, после всех элементов с данными.

3. **Внутри элементов без данных:** Элементы без lastEvent сортируются по алфавитному порядку названий.

4. **Отсутствие на Home:** Элементы без lastEvent не показываются на Home (недостаточно данных).

### 13.5. Items with Equal Urgency in All Aspects

**Сценарий:** Два элемента имеют одинаковую категорию срочности, одинаковое remainingDays, одинаковое remainingKm.

**Правило tie-breaking:**

1. **Алфавитный порядок:** Используется алфавитный порядок по названию элемента для стабильной сортировки.

2. **Стабильность:** Порядок элементов с одинаковой срочностью должен быть стабильным при повторных загрузках.

3. **Предсказуемость:** Пользователь может ожидать, что элемент с названием, идущим раньше в алфавитном порядке, будет выше элемента с названием, идущим позже.

## 14. Acceptance Criteria (Priority & Sorting)

### 14.1. Most Urgent Item Always First

**Критерий:** Наиболее срочный элемент всегда первый в списке.

**Pass Criteria:**

1. **OVERDUE всегда первый:** Если есть элементы OVERDUE, они всегда выше всех элементов SOON, OK и UNKNOWN.

2. **Самый просроченный OVERDUE первый:** Среди элементов OVERDUE, наиболее просроченный (наибольшее отрицательное значение) всегда первый.

3. **Самый срочный SOON после OVERDUE:** Если нет элементов OVERDUE, наиболее срочный элемент SOON (наименьшее remainingDays) всегда первый.

4. **Визуальная согласованность:** Визуальное представление (текст и индикатор) соответствует позиции в списке. Наиболее критичный элемент визуально наверху.

**Fail Criteria:**

- Элемент с более низкой срочностью появляется выше элемента с более высокой срочностью
- OVERDUE элемент не первый, если есть элементы SOON/OK/UNKNOWN
- Наиболее просроченный OVERDUE не первый среди OVERDUE элементов

### 14.2. Urgency Strictly Decreases Downward

**Критерий:** Срочность строго убывает сверху вниз в списке.

**Pass Criteria:**

1. **Монотонное убывание:** Каждый следующий элемент в списке имеет срочность, равную или меньшую, чем предыдущий элемент.

2. **Отсутствие инверсий:** Нет случаев, когда элемент с более высокой срочностью появляется ниже элемента с более низкой срочностью.

3. **Согласованность категорий:** Категории срочности убывают сверху вниз: OVERDUE → SOON → OK → UNKNOWN.

4. **Согласованность внутри категорий:** Внутри одной категории элементы с меньшим remainingDays выше элементов с большим remainingDays.

**Fail Criteria:**

- Элемент с более высокой срочностью появляется ниже элемента с более низкой срочностью
- Категории срочности не убывают сверху вниз
- Внутри категории элементы с большим remainingDays выше элементов с меньшим remainingDays

### 14.3. Top Priority Identification Without Reading All Items

**Критерий:** Пользователь может определить элемент с наивысшим приоритетом, не читая все элементы в списке.

**Pass Criteria:**

1. **Визуальная индикация приоритета:** Визуальный индикатор позволяет определить наиболее критичный элемент при быстром сканировании списка сверху вниз.

2. **Первый элемент = наивысший приоритет:** Первый элемент в списке всегда имеет наивысший приоритет среди всех элементов.

3. **Отсутствие необходимости сканирования:** Пользователь не должен сканировать весь список для поиска наиболее критичного элемента. Первый элемент всегда наиболее критичный.

4. **Glance mode поддержка:** Визуальный индикатор первого элемента позволяет определить его критичность без чтения текста.

**Fail Criteria:**

- Пользователь должен сканировать весь список для поиска наиболее критичного элемента
- Первый элемент не является наиболее критичным
- Визуальный индикатор не позволяет определить приоритет первого элемента

### 14.4. Sorting Feels Logical and Consistent Across Home and Items

**Критерий:** Сортировка воспринимается как логичная и консистентная между экранами Home и Items.

**Pass Criteria:**

1. **Одинаковая логика:** Логика сортировки одинакова на обоих экранах. Элементы с одинаковой срочностью имеют одинаковую позицию относительно друг друга на обоих экранах.

2. **Предсказуемость:** Пользователь может предсказать порядок элементов на Items, основываясь на порядке на Home (для элементов, присутствующих на обоих экранах).

3. **Логичность:** Порядок сортировки логичен и интуитивен. Пользователь не испытывает удивления от порядка элементов.

4. **Отсутствие противоречий:** Нет случаев, когда элемент выше другого на Home, но ниже на Items (для элементов, присутствующих на обоих экранах).

**Fail Criteria:**

- Логика сортировки отличается между Home и Items
- Элемент выше другого на Home, но ниже на Items (при одинаковых данных)
- Порядок сортировки нелогичен или противоречив
- Пользователь испытывает удивление от порядка элементов

### 14.5. No Visually Urgent Item Appears Below a Less Urgent One

**Критерий:** Элемент с визуально более срочным статусом не появляется ниже элемента с визуально менее срочным статусом.

**Pass Criteria:**

1. **Визуальная согласованность с сортировкой:** Визуальное представление (текст и индикатор) соответствует порядку сортировки. Элемент с более критичным визуальным индикатором всегда выше элемента с менее критичным индикатором.

2. **Отсутствие визуальных инверсий:** Нет случаев, когда элемент с критическим визуальным индикатором (например, красный) появляется ниже элемента с нормальным индикатором (например, зеленый).

3. **Согласованность текста и индикатора:** Текст и визуальный индикатор согласованы с позицией в списке. Элемент с текстом "Просрочено" всегда выше элемента с текстом "~30 дней".

4. **Поддержка визуального сканирования:** Пользователь может визуально сканировать список сверху вниз и видеть убывание срочности.

**Fail Criteria:**

- Элемент с критическим визуальным индикатором появляется ниже элемента с нормальным индикатором
- Текст и индикатор не согласованы с позицией в списке
- Визуальное сканирование показывает инверсии срочности
- Пользователь видит визуально более срочный элемент ниже менее срочного
