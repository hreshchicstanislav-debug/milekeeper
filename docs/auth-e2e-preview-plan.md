## Почему E2E пока остановлены

Готового Preview с исправлениями нет, а существующая allowlist Supabase его
не допускает. Dashboard прямо указывает, что неподходящий redirect URL заменяется
Site URL: нельзя начинать OAuth с неподготовленного Preview и рисковать возвратом
на основной сайт.

Отдельный Vercel URL изолирует размещение приложения, но не Supabase. Первый вход
Google создаёт записи Auth; вход, refresh и logout изменяют состояние сессий.
Проверка изоляции с тестовыми записями также пишет в БД. Даже выделенные аккаунты
в production поэтому не соответствуют текущему запрету менять production-данные.
Logout использует существующий global signOut: нельзя тестировать личный аккаунт,
одновременно используемый на основном сайте, без риска завершить его сессии.

Настроить Preview безопасно возможно, но нужно предварительное разрешение
пользователя на создание и настройку тестовых ресурсов и новый deployment
(пункт 8 текущего задания). До него операции ограничены чтением и локальными
проверками.

## Минимальный рекомендуемый план после разрешения

1. Создать отдельный Supabase test project с пустой базой либо development branch
   **без копирования данных и Storage**. Проверить доступность тарифа и стоимость
   до создания. Для branch проверить унаследованные интеграции, функции и настройки;
   ничего не merge в основной Supabase. Новый самостоятельный project проще
   отделить от production-интеграций.
2. Подготовить в тестовой базе существующую схему из уже согласованной истории
   миграций, включая две миграции этапа 1. Это отдельная операция и тоже требует
   разрешения: сейчас никакие миграции не запускаются. Не создавать новые
   миграции и не менять схему production. Проверить тестовые RLS, grants и FK.
   Drift `odometer_entries.source` остаётся техническим долгом этапа 1;
   текущий код не использует столбец, удалять или синхронизировать его не нужно.
3. Создать отдельный Vercel test project, например `milekeeper-auth-e2e`,
   без автоматического deployment основного `main`. Это исключит наследование
   production-секретов из текущего проекта. Использовать отдельный временный
   checkout checkpoint `c550a4c`, без `.env.local`, `.env.vercel.production`,
   текущей `.vercel` и production backups. Не менять привязку рабочего репозитория.
4. Установить только тестовые переменные, перечисленные ниже, и ту же
   конфигурацию Node.js 24.x/Next.js/региона. Выполнить новую удалённую сборку
   с target **Preview**, без `--prod`, promotion и назначения production domains.
   Не загружать локальный prebuilt bundle, собранный с production env.
   Зафиксировать deployment URL, связь с checkpoint и успешный build.
5. На полученный точный HTTPS URL настроить Google OAuth и Supabase Auth
   **тестового** окружения. До завершения настройки вход не запускать.
   Не использовать широкую allowlist `https://*.vercel.app/**`.
6. Обеспечить доступ двух тестеров к Preview, сохранив защиту основного проекта.
   Проверить, что Vercel Authentication не прерывает callback. Выбрать один
   неизменный hostname для всего прогона и PWA; токены/cookies не переносить
   между alias и deployment URL.
7. Провести сценарии из таблицы ниже на настоящем Supabase Auth/Google OAuth.
   Использовать только синтетические данные в тестовой базе. Сохранить результаты
   без токенов, cookies, OAuth URL fragments и персональных данных.
8. После исправления обнаруженных дефектов повторить проверки, сверить production
   конфигурацию и согласовать отдельный production deployment. Preview с тестовыми
   Supabase-переменными **нельзя просто promote** в production: нужна сборка
   того же проверенного кода с production env, после отдельного разрешения.

### Тестовые переменные Vercel

| Переменная | Значение/правило |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_URL` | Один и тот же URL отдельного тестового Supabase |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_ANON_KEY` | Один и тот же anon key тестового проекта; никаких production ключей |
| `SUPABASE_SERVICE_ROLE_KEY` | Не задавать: auth E2E не требуют adminClient; keep-alive в этом прогоне не вызывается |
| `CRON_SECRET` | Отдельный случайный тестовый секрет; production секрет не копировать |
| `NEXT_PUBLIC_DEV_GUEST_MODE` | Не задавать или `0` |

Google client secret хранится только в настройках провайдера тестового Supabase,
не в браузере и не в `NEXT_PUBLIC_*`. Проверить отсутствие production env перед
сборкой. Отсутствие service_role исключает запись через adminClient в Preview;
это намеренно ограничивает проверку auth, а не проверяет серверный keep-alive.
Production keep-alive проверен ранее в этапе 1, заново здесь не вызывался.

### Google OAuth и Supabase URL — разные адреса

- Google Web OAuth client: Authorized redirect URI —
  `https://<TEST_SUPABASE_REF>.supabase.co/auth/v1/callback`.
  Предпочтительно отдельный тестовый client; действующий production client
  и его URI сохраняются. Указать HTTPS origin Preview в Authorized JavaScript
  origins согласно инструкции Supabase. Проверить audience, необходимые scopes
  `openid`, email/profile и доступ двух тестовых аккаунтов; при Testing добавить
  их в test users. Не расширять scopes ради этой проверки.
- Supabase тестового проекта: включить Google с тестовыми credentials;
  Site URL — `https://<EXACT_PREVIEW_HOST>`;
  Redirect URL — `https://<EXACT_PREVIEW_HOST>/auth/callback`.
  Не менять production Site URL/allowlist/provider.
- Если позднее будет отдельно разрешено тестирование на production Supabase,
  его Google callback URI останется прежним; Preview callback добавляется в
  Supabase allowlist. Однако этот вариант всё равно создаёт/меняет production
  Auth-данные и не разрешён текущими ограничениями.

## Матрица реальных E2E

Все перечисленные ниже сценарии сейчас **не выполнены**. Настройки Dashboard
прочитаны реальным браузером, но это не вход пользователя в приложение.

| Сценарий | Что нужно подтвердить при прогоне |
| --- | --- |
| Первый вход нового Google-пользователя A | Создание Auth пользователя только в тестовой базе; корректный callback; переход на главную после успешной sync |
| Повторный вход A | Тот же user ID, без дубликата; успешное восстановление cookies |
| Callback / отказ sync | При успешной sync — главная; при контролируемом сбое — ошибка и ручной retry; никакого цикла login ↔ главная |
| Reload и истечение access token | Сессия переживает reload и реальный refresh; браузерная и серверная части согласованы |
| Две вкладки одного профиля | Общая сессия, ротация без потери входа, нет бесконечных sync; logout отражается во второй вкладке |
| Logout и повторный вход | Проверенные результаты SDK и очистки cookies; reload не возвращает закрытую сессию; новый вход работает |
| Частичный сбой logout | Контролируемый отказ cookie endpoint/сети: видимая ошибка, нет ложного успеха; ручной retry завершает выход |
| Недоступность Supabase | Временно заблокировать запросы только тестового браузера; cookies и действующая сессия сохраняются; после восстановления запросы работают |
| HTTP 429 | Контролируемая подстановка 429 на refresh в тестовом браузере, соблюдение Retry-After и сохранность сессии; успешный реальный refresh после снятия сбоя |
| Изоляция A/B | Два отдельных браузерных профиля; синтетические записи A недоступны B через UI и API; связь события B с item A отклонена БД |
| Установленная PWA | На подходящем устройстве: установка Preview, Google callback, reload/перезапуск, выход и повторный вход; основной PWA не затрагивается |

Для отказов сети/429 требуется инструмент локальной сетевой fault injection
в тестовом браузере. В доступном сейчас CUA browser API перехват ответов не
подтверждён. Способ нужно проверить перед прогоном; если инструмента нет, эти
пункты остаются непроверенными. Не перегружать Supabase ради настоящего 429 и
не менять production rate limits. Подставленный 429 — проверка реакции приложения
в реальном браузере с реальной сессией, **не** доказательство получения 429 от
самого Supabase. Локальные тесты транспорта отдельно уже прошли.

Потребуется участие пользователя при Google login/2FA/CAPTCHA для двух выделенных
аккаунтов. Установленную мобильную PWA нужно проверить самостоятельно на iOS или
Android: подходящее тестовое устройство в текущей сессии не подтверждено.

## Решение о готовности

Код этапов 1 и 2 сохранён, основные автоматические проверки проходят с ранее
зафиксированными ограничениями tsc/lint. Безопасный Preview технически возможен
после разрешённой настройки изолированных ресурсов. Реальные OAuth E2E пока
не подтверждены, поэтому обновление основного сайта сейчас не рекомендовано.
После успешного прогона всех обязательных сценариев, отдельной проверки PWA
и подтверждения production-конфигурации можно рассматривать обновление основного
сайта с отдельным разрешением; известные tsc/lint ограничения остаются в отчёте.

Пользователю нужно разрешить создание тестовых Supabase/Vercel ресурсов, их
настройку, применение существующей схемы **только к тестовой базе**, настройку
тестового Google OAuth client, один Preview deployment и создание тестовых
Auth-пользователей при первом OAuth входе. Также нужны два выделенных Google
аккаунта и тестовое устройство для PWA. Разрешение на production deployment
или изменение production-данных в этот план не входит.
