### Фактический порядок настройки

1. Войти через Google. В production гостевой доступ к личным экранам сейчас отсутствует. [Middleware](../../src/middleware.ts#L94), [`authRedirect`](../../src/lib/auth/browserSession.ts#L190).
2. Добавить текущий одометр. Это полезно сразу и необходимо для записи любой замены, даже календарной. [Проверка в `addServiceEvent`](../../src/lib/actions/serviceActions.ts#L368).
3. Создать элемент: название, режим «по пробегу» или «по календарю», соответствующий положительный интервал и порог в днях. Порог по умолчанию — 30, допустим положительный целый до 365. [Форма](../../src/app/components/AddServiceItemForm.tsx#L324), [валидация](../../src/lib/actions/serviceActions.ts#L58).
4. Указать **последнюю известную замену**, а не выдумывать новую замену сегодня. Дату и пробег прошлой замены можно ввести; пробег должен быть положительным в форме и не превышать фактический максимальный одометр. Без события любой элемент имеет `UNKNOWN`. [Форма события](../../src/app/components/AddServiceEventForm.tsx#L244), [`addServiceEvent`](../../src/lib/actions/serviceActions.ts#L375), [`calcServiceStatus`](../../src/lib/service/calcServiceStatus.ts#L97).
5. Позднее записать более высокий одометр в другой календарный день. При положительном приросте появляется темп и оценка дней для километрового элемента. Старые показания не стоит обещать как произвольный импорт: обычное добавление требует превышения существующего максимума независимо от выбранной даты. [`addOdometerEntry`](../../src/lib/actions/odometerActions.ts#L157).

Создание элемента технически возможно раньше первого одометра, но записать замену до одометра нельзя. Если дата/пробег последней замены неизвестны, корректное состояние — отсутствие исходной точки, а не фиктивный «точный» срок. [Код проверки](../../src/lib/actions/serviceActions.ts#L368).

### Что обязательно для разных расчётов

| Результат | Минимально необходимые данные | Что дают дополнительные записи |
|---|---|---|
| Измеренная история | Одна запись пробега с датой | Новые факты, изменение пробега между записями |
| Остаток километров | Текущий фактический/расчётный пробег + элемент с км-интервалом + последнее событие | Более свежая контрольная точка; без темпа остаток всё равно считается |
| Календарный срок | Последнее событие с датой + интервал в днях + текущая дата | История пробега не требуется самой формуле; UI требует одометр для первоначальной записи события |
| Средний темп | Не менее двух разных дней с показаниями и положительный прирост в выбранном наборе | Обновление крайних точек/окна; не каждое промежуточное показание меняет темп |
| Расчётный текущий пробег | Опорный фактический замер + положительный конечный темп + прошедшие календарные дни | Коррекция оценки реальным замером и пересчёт темпа |
| Дни до км-замены | Всё для остатка км + положительный конечный темп | Пересчёт сроков на новой информации; гарантии точности нет |

Источники: [`calculateDailyMileageRateToBe`](../../src/lib/service/dailyMileageRateToBe.ts#L144), [`computeEstimatedOdometer`](../../src/lib/service/estimatedOdometer.ts#L68), [`calcServiceStatus`](../../src/lib/service/calcServiceStatus.ts#L122).

## 4. Прогнозирование: фактический алгоритм

### 4.1. Пять понятий, которые нельзя смешивать

1. **Измеренная история** — сохранённые `OdometerEntry`. Это введённые пользователем сведения, а не датчик или автоматическая телеметрия.
2. **Оценка темпа** — одно число км/день, выведенное из этой истории. Не список реально пройденных расстояний каждого дня.
3. **Расчётный текущий пробег** — продолжение последнего факта по этому темпу до выбранного «сейчас». Самостоятельного экрана графика будущей траектории нет; модель позволяет оценить значение на другом `now`.
4. **Срок обслуживания** — календарный срок от события либо оценка времени достижения километрового интервала.
5. **Уверенность** — отдельная эвристика частоты/свежести записей и флаг отображения. Статистическая ошибка модели, доверительный диапазон или процент точности не вычисляются.

Источники: [типы записей](../../src/lib/db/types.ts#L7), [темп](../../src/lib/service/dailyMileageRateToBe.ts#L144), [экстраполяция](../../src/lib/service/estimatedOdometer.ts#L68), [обслуживание](../../src/lib/service/calcServiceStatus.ts#L82), [эвристика](../../src/lib/prediction/dailyRate.ts#L85), [флаг UI](../../src/lib/service/serviceItemStatusVM.ts#L102).

### 4.2. Как выбирается история

Основные страницы вызывают `calculateDailyMileageRateToBe`, несмотря на историческое имя `ToBe`: это **уже действующий алгоритм**. Главная, список и деталь загружают только 50 последних записей по `occurred_at`. Поэтому расчётное окно — не гарантированно вся история за 60 дней: при частом вводе старые нужные точки могут не попасть в эти 50. [Главная](../../src/app/page.tsx#L85), [список](../../src/app/items/page.tsx#L28), [деталь](../../src/app/items/[id]/page.tsx#L30), [запрос истории](../../src/lib/actions/odometerActions.ts#L19).

Последовательность внутри функции:

1. Исключить записи с `occurred_at > now`.
2. Сгруппировать оставшиеся по локальному календарному дню среды выполнения; за день взять минимальный и максимальный одометр.
3. Выбрать дни от полуночи `today − 60 дней` до сегодня **включительно**.
4. Если из этого набора можно получить положительный темп, использовать его.
5. Иначе взять последние **14 дней с записями** из всей переданной истории, без предела возраста; попытаться посчитать темп по ним.
6. Если и это не удалось, вернуть `dailyRate: null`, `isFallback: false`, `reason: insufficient_data`.

Источник: [`buildDayBuckets`](../../src/lib/service/dailyMileageRateToBe.ts#L61), [`calculateDailyMileageRateToBe`](../../src/lib/service/dailyMileageRateToBe.ts#L144).

**Нюансы границ:** «60 дней» в UI — название окна; код вычитает 60 и включает оба края, то есть потенциально 61 календарную дату. «14 активных дней» — дни наличия записи, а не распознанные дни поездок и не последние 14 календарных дней. Дни без записей между крайними точками входят в знаменатель. Эти технические детали важны для воспроизводимых примеров, но не требуют длинного объяснения в приветствии.

### 4.3. Как считается км/день и когда он появляется

```text
прирост = максимум последнего дня − минимум первого дня
число дней = календарный промежуток между этими днями + 1
темп = прирост / число дней
```

Для успеха нужны минимум два различных дня и положительный прирост. Два показания в один день не дают темп, сколько бы километров между ними ни было. Показания в соседние календарные дни могут быть близки по часам: минимальный промежуток в часах не проверяется. Максимальный допустимый разрыв также не задан — fallback может использовать старые далеко разнесённые дни. [`computeFromBuckets`](../../src/lib/service/dailyMileageRateToBe.ts#L88).

Пример существующей формулы: 100 000 км 1 октября и 100 500 км 8 октября дают **500 / 8 = 62,5 км/день**, а не 500 / 7. Это проверяется и существующим [тестом редкого ввода](../../src/lib/service/__tests__/mileageAndForecastToBe.test.ts#L54).

Первый темп может появиться после второго подходящего показания уже на следующую календарную дату. Первый срок **километрового** обслуживания появится только если дополнительно есть текущий одометр, элемент с интервалом и событие замены. Календарный срок не ждёт второй записи одометра. [Темп](../../src/lib/service/dailyMileageRateToBe.ts#L88), [обслуживание](../../src/lib/service/calcServiceStatus.ts#L97).

### 4.4. Стабилизация и то, чего нет

Используются дневная группировка и окно истории; это усреднение общего прироста, но не статистическое сглаживание отдельных скоростей. Промежуточная запись, не меняющая крайние значения/выбор окна, может вовсе не изменить темп. Добавление записи не имеет гарантированно «плавного» эффекта. [Тест крайних точек](../../src/lib/service/__tests__/mileageAndForecastToBe.test.ts#L30), [формула](../../src/lib/service/dailyMileageRateToBe.ts#L100).

В действующей функции **нет** медианы, регрессии, весов по свежести, определения стоянки, фильтра выбросов, предельных км/день, оценки дисперсии или обучения модели. Очень большой положительный прирост крайних точек принимается как есть. В проверке в памяти прирост 120 000 км между двумя соседними датами дал 60 000 км/день: это диагностический пример отсутствия ограничения, не реалистичный демонабор.

В [`prediction/dailyRate.ts`](../../src/lib/prediction/dailyRate.ts#L16) действительно есть медианная `computeDailyRate`, но поиск вызовов в `src` не выявил её применения в основных страницах. Они импортируют оттуда только `computeConfidence`. Также комментарии и параметры в [`odometerForecast.ts`](../../src/lib/service/odometerForecast.ts#L9) упоминают 14-дневное окно, 20 записей, диапазон 1–1500 и fallback 30 км/день; исполняемые обёртки вызывают текущую функцию и эти параметры не реализуют. `estimateDaysToReachKm` имеет отдельный fallback 30 для неположительного темпа, но в основных экранах не вызывается. **При недостаточной истории основной прогноз не подставляет 30 км/день.**

### 4.5. Что происходит между замерами

Опорная запись выбирается через `getMaxMileageEntry` — **по максимальному пробегу**, не по последней дате. При обычном последовательном вводе они совпадают, но код не делает их тождественными. Изменение/удаление последней записи в истории выбирает запись по дате. [`getMaxMileageEntry`](../../src/lib/actions/odometerActions.ts#L101), [`getLatestOdometerEntry`](../../src/lib/actions/odometerActions.ts#L50).

```text
расчётный пробег сейчас = округлить(опорный пробег + целые календарные дни × темп)
```

Нет записи — нет значения. Нет положительного конечного темпа или прошло ноль календарных дней — показывается факт. Отрицательный промежуток времени ограничивается нулём. Расчётное значение не опускается ниже опорного факта и не записывается в БД. [`computeEstimatedOdometer`](../../src/lib/service/estimatedOdometer.ts#L68).

На главной при реальном превышении факта появляется «Расчётный пробег» и `~`, ниже сохраняются значение и дата последнего замера. В список и деталь для прогноза передаётся расчётный пробег, а в форму записи замены — **фактический**. [Главная](../../src/app/page.tsx#L519), [список](../../src/app/items/page.tsx#L53), [деталь/форма](../../src/app/items/[id]/ItemDetailsPageClient.tsx#L405).

Расчёт продолжает двигаться без нового ввода **при новом чтении/рендере**. Фонового ежедневного создания показаний нет. Динамические страницы получают `getAppNow`; в LIVE это текущее время. Не обнаружен таймер, ежедневно обновляющий открытый dashboard. Возможность пересчёта при запросе не гарантирует обновление страницы, которая оставалась открытой через полночь. [Режим времени](../../src/lib/appNow.ts#L53), [главная](../../src/app/page.tsx#L22), [клиентская оболочка](../../src/app/components/HomeContentClient.tsx#L14).

Риски времени: day-bucket использует локальную зону **среды исполнения**, а даты в `LocalDateTime` отображаются в зоне браузера. Главная/список рассчитываются на сервере, деталь снова вызывает `calcServiceStatus` на клиенте с `getAppNow`. Согласованность на полуночи, в разных зонах и на DST требует отдельной проверки. [Дневной ключ](../../src/lib/service/dailyMileageRateToBe.ts#L39), [клиентский расчёт](../../src/app/items/[id]/ItemDetailsPageClient.tsx#L162), [вывод дат](../../src/app/components/LocalDateTime.tsx#L48).

### 4.6. Что улучшает новый замер

- Даёт реальный одометр вместо накопленной экстраполяции и переносит опорную дату.
- Может пересчитать темп, если меняет край дня, край выбранного окна или выбор fallback.
- Пересчитывает остаток километров и дней до обслуживания.
- Может изменить эвристическую категорию частоты/свежести истории.
- Не обязан повысить точность, изменить среднее или приблизить дату замены. Более низкий реальный пробег, чем прежняя **оценка**, допустим, если он выше предыдущего **факта**, и может отодвинуть срок.

Источники: [валидация относительно факта](../../src/lib/actions/odometerActions.ts#L174), [темп](../../src/lib/service/dailyMileageRateToBe.ts#L100), [экстраполяция](../../src/lib/service/estimatedOdometer.ts#L99), [существующая регрессия калибровки](../../src/lib/service/__tests__/estimatedCurrentMileage.regression.test.ts#L138).

### 4.7. Обслуживание: километры и календарь

Для км-интервала: `следующая замена = пробег последней замены + interval_km`; `остаток км = следующая замена − расчётный текущий пробег`; при доступном темпе `остаток дней = ceil(остаток км / темп)`. Оценочная дата — локальное сегодня плюс это число дней. [`calcServiceStatus`](../../src/lib/service/calcServiceStatus.ts#L122).

Для календаря: дата последней замены приводится к локальной полуночи, затем добавляется `interval_days`. Особенность: `addCalendarDaysSkippingLeap` не считает 29 февраля в добавляемом интервале. Поэтому это не универсальное прибавление N × 24 часа. Пикер формы переводит годы/месяцы в `years × 365 + months × 30 + days`; «месяц» — фиксированные 30 дней, не всегда следующий календарный месяц. [Добавление дней](../../src/lib/service/calcServiceStatus.ts#L65), [пикер](../../src/app/components/AddServiceItemForm.tsx#L336).

**UI и возможности движка различаются:** обычная форма сохраняет только один интервал, скрытый отправляет `null`. В типах, server actions и расчёте могут быть оба интервала; такие записи, например, есть в исходниках dev-seed. [Форма](../../src/app/components/AddServiceItemForm.tsx#L474), [обновление](../../src/lib/actions/serviceActions.ts#L188), [dev-seed](../../src/lib/actions/devActions.ts#L101).

| Входные данные | Основной показатель и статус |
|---|---|
| Нет последней замены | `UNKNOWN` до рассмотрения интервалов |
| `measurement_mode = km` | Основной показатель всегда км; при отсутствии текущего пробега — `UNKNOWN`; дни только при темпе |
| `calendar`, только дни | Календарный остаток, история темпа не нужна |
| `calendar`, оба интервала | Если обе даты доступны, выбирается более ранняя; при равенстве — календарь. Без темпа выбирается календарная дата, км могут быть справочными |
| Любой режим после выбора доступного основного показателя | `OVERDUE`, если остаток км ≤ 0 **или** календарных дней < 0; иначе `SOON`, если прогнозные/календарные дни от 0 до `notify_before_days`; иначе `OK` |

Источник: [ветвление режима](../../src/lib/service/calcServiceStatus.ts#L195), [смешанные критерии](../../src/lib/service/calcServiceStatus.ts#L229), [статусы](../../src/lib/service/calcServiceStatus.ts#L336).

Следствие: нельзя универсально описывать движок как «всегда выбирает, что наступит раньше». В км-режиме с двумя интервалами основным остаётся км, хотя просроченный календарь может сделать общий статус `OVERDUE`. Без темпа километровый `SOON` не определяется по малому остатку км; уже достигнутый км-интервал всё равно даёт `OVERDUE`. Календарный срок сегодня — 0 дней и ещё `SOON`, километровый остаток 0 — уже `OVERDUE`.

Поле `why` не всегда точно описывает причину в смешанных режимах: например, календарный режим может быть просрочен по км, но строка формируется как «Просрочено по календарю». Это ограничение текста, а не новый алгоритм. [Формирование `why`](../../src/lib/service/calcServiceStatus.ts#L368).

### 4.8. Уверенность и оформление

`computeConfidence` — **эвристическая категория**, не измеренная точность:

- `high`: ≥ 6 записей за последние 30 суток и последняя запись не старше 3 дней;
- `medium`: ≥ 4 записей за последние 60 суток и последняя не старше 7 дней;
- иначе `low`.

Использует `new Date()`, не переданный AppNow; считает записи, не разные дни; отдельного исключения будущих записей нет. `getDaysSinceLastEntry` берёт `entries[0]`, предполагая сортировку по дате. [`computeConfidence`](../../src/lib/prediction/dailyRate.ts#L85).

Флаг `isPredictionReliable` в VM = положительный темп **и** `confidence !== low`. На главной confidence передаётся, в списке — `undefined`: там при том же темпе флаг может стать `true`, даже если главная считает историю слабой. Fallback напрямую флаг не понижает. У календарного элемента без темпа может появиться подсказка о редком пробеге, хотя его календарный срок известен; у элемента без замены флаг может быть `true` при `remainingDays = null`. [`buildServiceItemStatusVM`](../../src/lib/service/serviceItemStatusVM.ts#L102), [вызов на главной](../../src/app/page.tsx#L373), [вызов списка](../../src/app/items/page.tsx#L69).

Цвет полосы определяется `OVERDUE` либо долей оставшегося интервала: >25% зелёный, >10% жёлтый, >3% оранжевый, иначе красный; при отсутствии доли — жёлтый. Поэтому красная полоса сама по себе **не равна** просрочке. `statusText` выводится из остатка дней; месяцы отображения также делятся на 30. [VM](../../src/lib/service/serviceItemStatusVM.ts#L106), [формат времени](../../src/lib/format/formatServiceTime.ts#L34).

На главной компонент компактной строки дополнительно использует категории по остатку дней (<0, ≤10 и т. д.). Нельзя обещать, что цвет главной и списка — один и тот же классификатор. [`HomeSoonMaintenanceBlock.getCategory`](../../src/app/components/HomeSoonMaintenanceBlock.tsx#L97).

В словаре есть тексты «Прогноз точный» и «точность на 3 дня», но актуальный `HomeAdaptiveContent` отображает только низкую категорию при наличии хотя бы одной записи. Эти строки словаря не подтверждают реальную измеренную точность и не должны переноситься в onboarding. [Словарь](../../src/lib/copy/ru.ts#L55), [условие отображения](../../src/app/components/HomeAdaptiveContent.tsx#L29).

### 4.9. Старая история и нетипичная эксплуатация

Если последние 60 дней не дают темпа, старые 14 дней с показаниями могут всё ещё его дать. Возраст последнего замера не обнуляет скорость, экстраполяция не имеет ограничения по горизонту. На главной категория может стать `low`, но расчёты продолжаются. Если машина долго стояла, продана, резко изменила режим поездок или в крайний замер закралась ошибка, модель сама этого не узнает. [Fallback](../../src/lib/service/dailyMileageRateToBe.ts#L167), [экстраполяция](../../src/lib/service/estimatedOdometer.ts#L99), [эвристика](../../src/lib/prediction/dailyRate.ts#L104).

Нулевая/отрицательная общая разница в выбранном наборе не даёт положительного темпа; функция пробует fallback и при его неуспехе возвращает null. Повторить прежний одометр через обычную форму добавления нельзя: действует строгое превышение максимума. Будущее показание исключается из темпа, но `getMaxMileageEntry` не фильтрует его по времени; поэтому его использование как опоры — отдельный возможный крайний случай. [Темп](../../src/lib/service/dailyMileageRateToBe.ts#L106), [запрос максимума](../../src/lib/actions/odometerActions.ts#L101).

### Подтверждённые пробелы, которые нельзя прикрывать презентацией

1. После создания элемента человек не получает на главной подключённого приглашения записать последнюю замену.
2. Список пишет «Недостаточно данных» и при отсутствующей замене, и при существующем км-остатке без темпа; причины лучше различать в будущей концепции.
3. Эвристика надёжности неодинакова на главной и в списке; календарный срок может сопровождаться нерелевантной подсказкой о пробеге.
4. Даты/цвета смешанных элементов и объяснение `why` не всегда соответствуют общему статусу.
5. В календарной детали дата следующей замены рендерится из `statusResult.primary.dueDate`, но `calcServiceStatus` записывает timestamp в `dueValue`, не присваивая `dueDate`. Поэтому по коду строка даты может показывать «—» при корректном остатке дней. [Место вывода](../../src/app/items/[id]/ItemDetailsPageClient.tsx#L364), [сборка результата](../../src/lib/service/calcServiceStatus.ts#L411). В браузере этот календарный случай не воспроизведён.

Это наблюдения и ограничения исследования. Исправления в рамках этой задачи не выполнены и не считаются согласованными.

## 6. Ценность для пользователя и портфолио

Это **продуктовая оценка на основе кода**, не результат интервью или аналитики.

| Ценность | Почему существенна | Основание |
|---|---|---|
| Видеть, что обслуживать ближайшим | Главная отбирает просроченное и близкое; не нужно вручную сопоставлять все интервалы | [`pickSoonMaintenanceItems`](../../src/lib/home/soonMaintenance.ts#L110) |
| Переводить км-интервал в понятные дни | Порог 30 дней означает разное расстояние при разном темпе поездок | [`calcServiceStatus`](../../src/lib/service/calcServiceStatus.ts#L151) |
| Учитывать время между замерами | Текущая оценка меняется при чтении, пока фактическая история остаётся прежней | [`computeEstimatedOdometer`](../../src/lib/service/estimatedOdometer.ts#L68) |
| Проверить, откуда взялся срок | Вкладка расчёта раскрывает последнее обслуживание, одометр, интервал и средний темп | [`ItemDetailsPageClient`](../../src/app/items/[id]/ItemDetailsPageClient.tsx#L253) |
| Сохранять историю замен | Следующий интервал опирается на последнее событие, предыдущие остаются в истории | [События](../../src/lib/actions/serviceActions.ts#L422) |

Для портфолио наиболее убедителен путь «история → темп → расчётный пробег → срок → новый факт → пересчёт». Дополняют его календарное обслуживание, история замен, понятная мобильная навигация и RU/EN. Google OAuth/RLS и PWA-оболочку можно объяснять в отдельном описании проекта, но они сами не показывают пользу пустого приложения. Не следует представлять продукт как AI-прогноз, диагностику технического состояния, доказанную точность ±N дней, автопарк, offline-синхронизацию или систему push-напоминаний.

## 7. Можно ли использовать текущий код для изолированной демонстрации

| Часть | Фактическая возможность повторного использования | Ограничение |
|---|---|---|
| Расчёт темпа, оценки одометра, статуса, VM, отбора и сортировки | Принимают массивы/объекты и переданное время, не требуют Supabase; прямое исполнение в памяти подтвердило возможность | Эвристика `computeConfidence` отдельно читает реальное время |
| `StatusRowDetail`, `StatusRowCompact`, форматирование | Получают отображаемые props и локализуют системные строки | Подсказки/цвета имеют описанные ограничения; сами строки не являются полноценным экраном |
| `ItemsPageClient`, главная/деталь | Можно использовать части отображения после выделения зависимостей | Внутри текущих страниц есть live-загрузчики, маршруты, формы, API истории и `router.refresh` |
| Формы одометра, элемента, замены | Внешний вид потенциально пригоден | Прямо импортируют server actions, а не переданный обработчик; синтетические props не отменяют реальную запись |
| DevTools seed/simulation/reset | Есть готовые примеры данных и инструменты для разработки | `seedDemoData`, `simulateTripRange`, `wipeAllData` работают с реальной БД владельца; reset удаляет его записи; использовать их как публичное демо нельзя |
| TEST/AppNow и dev-guest | Есть тестовое время, гостевой обход только вне production | TEST хранит настройки в общих localStorage/cookies и не выбирает изолированное хранилище; dev-guest не является production-демо |

## 8. Непроверенное и требующее следующего решения

**Осталось непроверенным:** все пустые состояния в браузере с отдельными аккаунтами; OAuth E2E новой/истёкшей сессии в этой задаче; schema drift live-базы; полуночные переходы/разные часовые зоны/DST; PWA installation/offline на реальном устройстве; календарная строка даты в production; пользовательское понимание прогноза и фактическое изменение его ошибки от частоты ввода. Существующий release-report также оставляет ручную OAuth-приёмку отдельно.

**Требует решения владельца:** концепция публичного демо, степень интерактивности, формат демодаты, условия первого показа, место повторного открытия, отдельный объём исправлений описанных UX-пробелов. Эти решения сформулированы в [предложении](02-onboarding-proposal.md#10-вопросы-для-согласования).

**Выполнено сейчас:** исследование и два Markdown-документа. Прикладной код, тесты, схемы, Supabase, production и авторизация не изменялись; миграции, deployment, commit, push и merge не выполнялись.
