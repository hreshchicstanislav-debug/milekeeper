# Ошибка Google callback: rollback и исправление sync

Дата: 09.10.2026, Алматы. Изменения приложения повторно не опубликованы.

## Восстановление основного сайта

После анализа логов выполнен разрешённый rollback:

- С неисправного `dpl_9M6xLttVHnwgZmp5zEWY4QCgduTH` (код `950b6bf`).
- На предыдущий `dpl_6YuVrfWqNToSyhqRRVn4HKhSNfWM`, код
  `446ab00c19332f6d5c66803fd11ef22b55b61970`.
- Read-only API Vercel подтвердил этот ID в `targets.production`, READY.
- https://milekeeper.vercel.app/login и manifest отвечают 200;
  главная без cookies завершает перенаправление на login без цикла.
- Пользователь после rollback сообщил: «сейчас могу залогиниться».
  Агент не выполнял реальный OAuth-вход; исправленная версия ещё не проверена
  реальным входом.

Rollback не удалил ветку `codex/auth-security-stage-2`, её коммиты или файлы
этапов 1 и 2. Ограничения БД этапа 1 остаются в production; приложение этапа 2
временно снято с основного сайта. Supabase, Google provider, env и бизнес-данные
пользователей не изменялись; миграции не выполнялись. Vercel после rollback
установил `autoAssignCustomDomains=false`; повторная публикация требует
явной promotion. [Правила rollback](https://vercel.com/docs/cli/rollback).

## Фактическая причина и доказательства

В доступных runtime logs неисправного deployment callback имеет HTTP 200,
а sync — 400, включая запрос 09.10.2026 00:03:40.779 Алматы. Логи не содержат
пользовательского request body; реальные токены не извлекались.

`getSession()` SDK возвращает полную Session: кроме двух токенов в ней
обязательны `expires_in`, `token_type`, `user`, возможны `expires_at` и OAuth
provider fields. Это проверено в установленном исходном коде
`node_modules/@supabase/auth-js/src/lib/types.ts` и
[API getSession](https://supabase.com/docs/reference/javascript/auth-getsession).

`BrowserSession.synchronize()` передаёт `data.session` в `postSessionSync()`.
До исправления функция сериализовала весь полученный объект. TypeScript тип
`SessionTokens` не удаляет дополнительные свойства JavaScript объекта.
Endpoint намеренно отклоняет JSON с любыми полями кроме `access_token` и
`refresh_token`; полный SDK объект поэтому всегда отвергался до validateSession.
HTTP 400 превращался в общее сообщение ошибки и не разрешал переход на главную.

На сохранённом URL неисправного deployment это воспроизведено HTTP-запросом
с **синтетическими** токенами и формой полной Session: правильные Origin и
Content-Type, ответ 400 `missing or invalid tokens`. Ответ доказывает прохождение
проверок Origin/Content-Type и отказ именно на проверке полей. Запрос с теми же
двумя синтетическими токенами без дополнительных полей прошёл проверку формы,
но был отклонён дальше с 503 `Authentication temporarily unavailable`: невалидные
синтетические credentials не являются подтверждением работы Supabase Auth.
Действительные пользовательские токены, refresh или cookies для диагностики
не передавались; Auth-сессии пользователей не изменялись.

До изменения два новых теста воспроизвели проблему: сериализатор передавал
лишние поля, а полный путь через реальный Next route возвращал отказ вместо
синхронизации. После изменения оба проходят. Прежние тесты проверяли только
заранее сокращённые пары, поэтому не обнаружили несовпадение SDK Session и
HTTP-контракта. Предыдущий production smoke проверял отказ некорректных
запросов, а не успешный sync полноценной Session — этого было недостаточно.

## Исправление и проверенные участки

Единственное изменение рабочего кода — явная проекция двух полей в
`src/lib/auth/sessionSync.ts`. Дополнительные OAuth provider tokens, user и
метаданные не отправляются, включая повтор после временной ошибки.
Endpoint, его ограничения и настройки безопасности не ослаблены.

Проверены callback, AuthGate, browserSession, sessionSync, validateSession,
refreshSession и координация вкладок. При исходном 400 сервер не доходил до
валидации AT, обмена RT, сравнения user_id/session_id и записи cookies, поэтому
ротация и SDK adoption не были причиной **этого** отказа. Эти участки сохранены.
Новый интеграционный тест проверяет их связность с полной SDK Session:
getUser → refresh → проверка владельца/сессии → одинаковая пара в cookies и
ответе → setSession в браузере → authed. Параллельные вызовы callback/gate
используют один sync; повторный сигнал не запускает новую ротацию.

Файлы кода и тестов:

- `src/lib/auth/sessionSync.ts` — нормализованный request body.
- `src/lib/auth/__tests__/sessionSync.test.ts` — полная Session, provider fields,
  большой provider token и повторный запрос без передачи лишних полей.
- `src/app/api/auth/__tests__/routes.test.ts` — полная типизированная SDK Session
  через BrowserSession, настоящий сериализатор и настоящий строгий route;
  только upstream Supabase transport подменён.

Это интеграционные автоматические тесты, не Google OAuth E2E.

## Проверки

| Проверка | Результат |
| --- | --- |
| Две регрессии до исправления | Обе падают, остальные 73 теста выбранных файлов проходят |
| Полный `npm test` после исправления | 330 тестов, 24 файла — успешно |
| `npm run build` | Успешно |
| `npx tsc --noEmit --incremental false` | Ровно прежние 14 ошибок; вывод совпадает с baseline выпуска |
| `npm run lint` | Прежняя ошибка `next lint`; lint фактически не выполнен |
| `git diff --check` | Успешно |
| Сохранность этапа 1 | Миграции, отчёт и SQL-runner совпадают с `7705929` |

SQL-тесты повторно не запускались: исправление касается клиентского транспорта,
БД и миграции не меняются. Их успешный результат предыдущего выпуска сохранён.
Других существенных причин именно наблюдаемого 400 не обнаружено. Работу
обновлённого кода с настоящей Auth-сессией нужно подтвердить перед принятием
повторного выпуска; локальные transport mocks этого не заменяют.

## Безопасная повторная публикация — только после отдельного разрешения

1. Взять коммит исправления из текущей ветки; повторить основные проверки
   при новых изменениях, подтвердить существующие production env и сохранить
   работающий rollback ID `dpl_6YuVrfWqNToSyhqRRVn4HKhSNfWM`.
2. Собрать на существующем Vercel production project с production env и
   `--prod --skip-domain`, без миграций и изменения основного домена.
3. Проверить сборку, HTTP-контракт sync, защиты endpoints и отсутствие
   неожиданных ошибок. OAuth на отдельном URL пока не проверять: разрешён
   callback основного сайта, allowlist Supabase не менять без разрешения.
4. В согласованное время, при участии пользователя, явно promote проверенный
   deployment. Открыть новую загрузку login на основном адресе и немедленно
   проверить настоящий Google-вход → главная → reload → logout → повторный вход,
   затем две вкладки и PWA. Результат фиксировать без токенов и cookies.
5. При повторном сбое сразу rollback на сохранённый рабочий deployment.
   Не объявлять OAuth успешным по одному HTTP 200 callback.

Сейчас эти действия не выполнялись. Main не менялся; его старый код не следует
автоматически публиковать поверх будущего исправленного выпуска.
