### Отдельный технический долг: происхождение `source`

Фактический столбец: `source text NOT NULL DEFAULT 'user'`. Комментарий production
указывает назначение: `user` для пользовательских записей и `dev_sim` для
симуляции. Сейчас все 63 записи имеют `source = 'user'`; других значений нет.
Зависимости столбца — default и B-tree индекс `idx_odometer_entries_source`.
В публичных функциях, связанных с одометром, ссылок на `source` нет. Политики,
guardrail-триггеры и новые внешние ключи этот столбец не используют.

Текущий код не читает, не фильтрует и явно не записывает `source`; интерфейс
`OdometerEntry` его не объявляет. Запросы `select('*')` получают дополнительное
поле, но бизнес-логика его игнорирует; вставки используют default базы.
Dev-записи по-прежнему распознаются по note, а не по этому столбцу.

В Git-истории нет создания столбца/индекса ни в миграциях, ни в соответствующих
actions/types. Коммит `8cca9ee` от 08.01.2026 добавил документацию AppMode с
намерением разделять ручные и симулированные записи; она использовала названия
`manual`/`simulated`. Старые аудиты заявляли отсутствие `source` на основании
кода/миграций; это не соответствует нынешней production-схеме.
Точная дата, автор и способ создания production-объектов не установлены:
изменение не зафиксировано в доступной истории Git и `schema_migrations`.

Отдельно рекомендуется подготовить миграцию для воспроизводимости схемы с нуля:
добавление фактического `source`, его комментария и индекса, с проверкой уже
существующих объектов. Решение о дальнейших значениях и использовании в коде
нужно согласовать отдельно. Сейчас такая миграция **не создавалась и не применялась**.

## Исправления

1. `keep_alive_pings`: включён RLS без пользовательских политик; отозваны все
   права `PUBLIC`, `anon`, `authenticated` на таблицу и её identity sequence.
   Это закрывает также `TRUNCATE`, который RLS сам по себе не ограничивает.
   Серверная роль сохраняет чтение, вставку, удаление старых пингов и использование
   sequence. Маршрут keep-alive продолжает использовать существующий admin client;
   ключи и клиентский код не изменялись.
2. `service_events`: составной FK `(user_id, service_item_id)` ссылается на
   `service_items(user_id, id)`. Он проверяет владельцев при INSERT/UPDATE и
   препятствует смене владельца родительской записи, нарушающей связь. Проверка
   действует и для роли, обходящей RLS. Сохранён `ON DELETE CASCADE`.
3. `addServiceEvent`: перед вставкой проверяет доступность элемента по `id` и
   текущему `user_id`, возвращая понятную ошибку для отсутствующего/чужого элемента.
   Окончательную защиту от гонок и прямых запросов обеспечивает FK.

Существующие миграции, пользовательские RLS-политики, UI, PWA, вход и регистрация
не менялись. Этапы 2–5 не выполнялись.

- `supabase/migrations/20261008133712_restrict_keep_alive_access.sql` — RLS,
  отзыв прав обычных ролей и сохранение необходимых прав серверной роли.

  удаление прежнего FK только после успешной проверки нового.

Каждая миграция транзакционная, с `lock_timeout = '5s'`. Данные не обновляются и
не удаляются. При несовпадении владельцев в существующих записях вторая миграция
целиком откатывается. Старый FK остаётся на месте. Миграции независимы: успешная
первая не откатывается при отказе второй.

Существующий индекс `service_events(user_id, service_item_id, occurred_at DESC)`
покрывает столбцы дочернего FK. Дополнительный индекс событий не создаётся.

## Автоматические проверки

Из корня приложения:

```sh
npm test
npm run test:db-security
node node_modules/typescript/bin/tsc --noEmit --incremental false
npm run lint
npm run build
```

`test:db-security` требует Python 3 и локальные `initdb`, `pg_ctl`, `psql`.
Можно указать каталог PostgreSQL через `PG_BIN`. Скрипт создаёт временный кластер
с отдельным Unix socket и выключенным TCP, игнорирует унаследованные `PG*`
параметры подключения, применяет миграции и останавливает/удаляет кластер после
проверки. Он не принимает адрес существующей базы и не подключается к Supabase.
SQL-файлы в `supabase/tests` предназначены только для этого runner, не для запуска
на production. Это собственный набор SQL assertions, а не pgTAP.

Проверены реальные ограничения, grants и RLS в PostgreSQL 16.11. Supabase-роли
и интерфейс `auth.uid()` смоделированы тестовой bootstrap-функцией; используются
два синтетических пользователя. Production работает на PostgreSQL 17.6.

Проверки включают:

- запрет SELECT/INSERT/UPDATE/DELETE/TRUNCATE и прав sequence для обеих обычных
  ролей на keep-alive; дополнительную защиту RLS при повторном предоставлении CRUD;
- серверную вставку и очистку пингов после включения RLS;
- создание и изменение собственных событий;
- чужие связи при INSERT/UPDATE и обход RLS серверной ролью;
- запрет чтения/изменения/удаления чужих событий;
- сохранение прежних записей после миграции;
- каскадное удаление своих событий без удаления событий другого пользователя;
- отказ и полный откат миграции при заранее созданной некорректной связи.

Результат 08.10.2026:

| Проверка | Результат |
| --- | --- |
| `npm test` | Успешно: 191 тест в 17 файлах, включая 9 новых |
| `npm run test:db-security` | Успешно: миграции, ограничения/RLS, сохранение данных и откат |
| Отдельный `tsc --noEmit` | 14 существующих ошибок в пяти старых тестовых файлах; тот же набор воспроизведён на исходном HEAD в отдельном временном каталоге |
| `npm run lint` | Команда `next lint` не работает при установленном Next.js 16.1.1; этот script уже был в исходном HEAD, ESLint не настроен |

### Исходный порядок применения

На исходной проверке до применения RLS keep-alive был выключен, пользовательских
политик для него не было; FK событий проверял лишь `service_item_id`.
Несовпадений владельцев было 0. История production совпадала с
10 исходными миграциями репозитория; две новые миграции тогда ещё не применялись.

1. Получить отдельное разрешение пользователя на применение этих двух миграций.
2. Непосредственно перед применением повторить preflight и сверить историю
   миграций/целевой проект `nsmdouxbxajiyjqxgqml`. Не запускать сброс базы.
3. Применить две новые миграции в указанном порядке в период невысокой нагрузки:
   UNIQUE/FK требуют блокировок. При lock timeout повторить позже; не отключать
   ограничения. Если обнаружены некорректные связи — отдельно согласовать их
   исправление, не удалять пользовательские события автоматически.
4. После применения проверить RLS/grants, статус валидации FK, реальный cron
   keep-alive, добавление замены и историю под двумя тестовыми аккаунтами.
   При проверке через Data API запрещённые операции не должны возвращать данные
   или изменять таблицы.

Read-only preflight:

```sql
SELECT count(*) AS mismatched_owners
FROM public.service_events e
JOIN public.service_items i ON i.id = e.service_item_id
WHERE e.user_id IS DISTINCT FROM i.user_id;

SELECT relrowsecurity
FROM pg_class WHERE oid = 'public.keep_alive_pings'::regclass;

SELECT policyname, roles, cmd FROM pg_policies
WHERE schemaname = 'public' AND tablename = 'keep_alive_pings';

SELECT conname, convalidated, pg_get_constraintdef(oid)
FROM pg_constraint WHERE conrelid = 'public.service_events'::regclass
  AND contype = 'f';
```

Это исходный план, составленный до применения. Текущее состояние production и
выполненные проверки приведены в начале отчёта. Полные Supabase Auth/PWA browser
flows и запуск Vercel cron после миграций остаются непроверенными. Линтер и
отдельный TypeScript-check не дают полностью зелёный набор проверок из-за исходных
проблем проекта. Deployment не запускался.
