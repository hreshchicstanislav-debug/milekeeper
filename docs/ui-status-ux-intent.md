# UI Status UX Intent and Constraints

**Дата создания:** 2025-01-02  
**Цель:** Определить пользовательские цели, ограничения и принципы для статусного UI (без конкретных визуальных решений)  
**Область:** Мобильный UI (Home и Items экраны)

---

## 1. Primary User Goals

### 1.1. Understanding at a Glance (Понимание с первого взгляда)

**Цель пользователя:** Мгновенно понять общее состояние элементов обслуживания без детального чтения.

**Что должно быть понятно:**
- Есть ли элементы, требующие немедленного внимания (критический статус)
- Есть ли элементы, требующие внимания в ближайшее время (предупреждающий статус)
- Все ли элементы в порядке (нормальный статус)

**Когнитивная нагрузка:** Пользователь должен получить общее представление о состоянии за время, не превышающее 2-3 секунды просмотра списка.

### 1.2. Specific Information Access (Доступ к конкретной информации)

**Цель пользователя:** Получить конкретную информацию о статусе элемента для принятия обоснованного решения.

**Что должно быть доступно:**
- Конкретное значение времени до следующего обслуживания (количество дней)
- Индикация просроченных элементов
- Индикация ненадежности прогноза (когда данные недостаточны)

**Когнитивная нагрузка:** Пользователь должен получить конкретную информацию без необходимости перехода на детальную страницу элемента.

### 1.3. Decision Support (Поддержка принятия решений)

**Цель пользователя:** Принять решение о приоритетах обслуживания на основе статуса элементов.

**Что должно поддерживать принятие решений:**
- Сравнение срочности между элементами
- Понимание относительной важности (какой элемент требует внимания раньше)
- Оценка временных рамок для планирования

**Когнитивная нагрузка:** Пользователь должен иметь достаточно информации для принятия решения без дополнительных вычислений или интерпретаций.

## 2. Contextual Differences (Home vs Items)

### 2.1. Home Screen Context

**Роль:** Dashboard / Overview / Prioritization

**Пользовательский сценарий:**
- Пользователь открывает приложение для быстрого обзора состояния
- Пользователь хочет понять, что требует внимания прямо сейчас или в ближайшее время
- Пользователь принимает решение о приоритетах: что делать в первую очередь

**Информационные потребности:**
- Краткий обзор наиболее критичных элементов (до 5 элементов)
- Быстрое понимание общего состояния
- Поддержка принятия решений о приоритетах

**Временной контекст:**
- Быстрый просмотр (10-30 секунд)
- Периодические проверки (несколько раз в день или раз в день)
- Не требует детального изучения каждого элемента

**Эмоциональный контекст:**
- Пользователь хочет чувствовать контроль над ситуацией
- Пользователь хочет избежать неожиданностей (просроченные элементы)
- Пользователь хочет эффективно планировать обслуживание

### 2.2. Items Screen Context

**Роль:** Inspection / Comparison / Exploration

**Пользовательский сценарий:**
- Пользователь хочет просмотреть все элементы обслуживания
- Пользователь хочет сравнить статусы разных элементов
- Пользователь исследует состояние всех элементов для полного понимания

**Информационные потребности:**
- Полный список всех элементов
- Детальная информация о каждом элементе
- Возможность сравнения между элементами

**Временной контекст:**
- Более длительный просмотр (1-3 минуты)
- Менее частые проверки (раз в несколько дней или раз в неделю)
- Требует более детального изучения

**Эмоциональный контекст:**
- Пользователь хочет получить полную картину состояния
- Пользователь готов потратить больше времени на анализ
- Пользователь хочет быть уверенным, что ничего не пропущено

### 2.3. Key Differences Summary

| Аспект | Home | Items |
|--------|------|-------|
| **Основная цель** | Быстрый обзор и приоритизация | Детальный осмотр и сравнение |
| **Временной контекст** | Краткий просмотр (10-30 сек) | Длительный просмотр (1-3 мин) |
| **Количество элементов** | До 5 (только критичные) | Все элементы |
| **Информационная плотность** | Компактная, только необходимое | Детальная, полная информация |
| **Эмоциональный тон** | Спокойный, контролирующий | Информативный, всеобъемлющий |
| **Когнитивная нагрузка** | Минимальная для быстрого понимания | Допустима более высокая для детального анализа |

## 3. Cognitive Constraints

### 3.1. Information Processing Limits

**Ограничение:** Человеческий мозг может обработать ограниченное количество визуальной информации одновременно.

**Принцип:** Статус должен передаваться через минимальное количество визуальных сигналов, каждый из которых несет уникальную информацию.

**Риск нарушения:** Избыточные визуальные сигналы (дублирование информации) создают когнитивную нагрузку без добавления ценности.

### 3.2. Attention Hierarchy

**Ограничение:** Визуальное внимание пользователя следует определенной иерархии (от наиболее заметного к наименее заметному).

**Принцип:** Наиболее важная информация должна привлекать внимание первой, менее важная — второй, и так далее.

**Риск нарушения:** Конкуренция между визуальными элементами за внимание может замедлить понимание статуса или привести к пропуску важной информации.

### 3.3. Glance vs Detail Mode

**Ограничение:** Пользователь переключается между двумя режимами просмотра:
- **Glance mode:** Быстрое сканирование для общего понимания (1-2 секунды на элемент)
- **Detail mode:** Детальное изучение для конкретной информации (3-5 секунд на элемент)

**Принцип:** Статус должен поддерживать оба режима:
- Glance mode: общее понимание через быстрые визуальные сигналы
- Detail mode: конкретная информация через читаемый текст

**Риск нарушения:** Если статус оптимизирован только для одного режима, пользователь будет испытывать фрустрацию в другом режиме.

### 3.4. Memory and Recognition

**Ограничение:** Пользователь запоминает визуальные паттерны лучше, чем конкретные значения.

**Принцип:** Статус должен использовать узнаваемые визуальные паттерны для быстрого распознавания, но также предоставлять конкретные значения для точного понимания.

**Риск нарушения:** Если статус полагается только на абстрактные паттерны без конкретных значений, пользователь может неправильно интерпретировать состояние.

## 4. Visual Signal Principles (Abstract)

### 4.1. Signal Uniqueness (Уникальность сигнала)

**Принцип:** Каждый визуальный сигнал должен передавать уникальную информацию, не дублируя другие сигналы.

**Абстрактное описание:**
- Если используется категоризация (например, "критический", "предупреждающий", "нормальный"), она должна передаваться одним способом
- Если используется конкретное значение (например, "5 дней"), оно должно передаваться отдельным способом
- Если используется относительное значение (например, "75% осталось"), оно должно передаваться отдельным способом

**Цель:** Минимизировать визуальный шум и когнитивную нагрузку от избыточных сигналов.

### 4.2. Signal Hierarchy (Иерархия сигналов)

**Принцип:** Визуальные сигналы должны быть организованы в четкую иерархию важности.

**Абстрактное описание:**
- Наиболее важный сигнал (например, критический статус) должен привлекать внимание первым
- Второстепенный сигнал (например, конкретное значение) должен быть заметен при детальном просмотре
- Вспомогательный сигнал (например, относительное значение) должен быть доступен, но не конкурировать за внимание

**Цель:** Обеспечить быстрое понимание наиболее важной информации без перегрузки менее важными деталями.

### 4.3. Signal Accessibility (Доступность сигнала)

**Принцип:** Информация о статусе не должна полагаться только на один способ передачи (например, только на цвет).

**Абстрактное описание:**
- Если используется цвет для категоризации, должна быть альтернатива (например, текст или символ)
- Если используется визуальный паттерн, должна быть текстовая альтернатива
- Если используется относительное значение, должно быть конкретное значение

**Цель:** Обеспечить доступность для пользователей с различными способностями восприятия (дальтонизм, нарушение зрения, различные условия просмотра).

### 4.4. Signal Clarity (Ясность сигнала)

**Принцип:** Визуальные сигналы должны быть четкими и однозначными, не требующими интерпретации.

**Абстрактное описание:**
- Категоризация должна быть понятной без дополнительных объяснений
- Конкретные значения должны быть читаемыми и легко интерпретируемыми
- Относительные значения должны иметь четкий контекст (например, "75% от чего?")

**Цель:** Минимизировать время, необходимое для понимания статуса, и снизить вероятность неправильной интерпретации.

### 4.5. Signal Consistency (Консистентность сигнала)

**Принцип:** Визуальные сигналы должны быть консистентными между экранами, но адаптироваться к контексту.

**Абстрактное описание:**
- Одинаковые статусы должны передаваться одинаковыми сигналами на разных экранах
- Но визуальный вес сигналов может адаптироваться к контексту (например, более компактный на Home, более детальный на Items)
- Эмоциональный тон сигналов может адаптироваться к контексту (например, менее тревожный на Home, более информативный на Items)

**Цель:** Обеспечить узнаваемость и предсказуемость, сохраняя при этом оптимальность для каждого контекста.

## 5. Success Criteria (How We Know UI Works)

### 5.1. Glance Mode Success (Успех в режиме беглого просмотра)

**Критерий:** Пользователь может определить общее состояние элементов за время, не превышающее 2-3 секунды на элемент.

**Измеримые показатели:**
- Время до первого понимания статуса (должно быть < 1 секунды)
- Процент правильных определений статуса при быстром просмотре (должен быть > 90%)
- Отсутствие необходимости возвращаться к элементу для повторного просмотра

**Качественные показатели:**
- Пользователь чувствует уверенность в понимании статуса
- Пользователь не испытывает фрустрации от необходимости детального изучения
- Пользователь может быстро принять решение о приоритетах

### 5.2. Detail Mode Success (Успех в режиме детального просмотра)

**Критерий:** Пользователь может получить конкретную информацию о статусе без необходимости перехода на детальную страницу.

**Измеримые показатели:**
- Время до получения конкретной информации (должно быть < 3 секунд)
- Процент пользователей, которые находят конкретную информацию без перехода (должен быть > 80%)
- Отсутствие необходимости перехода на детальную страницу для понимания статуса

**Качественные показатели:**
- Пользователь чувствует, что имеет достаточно информации для принятия решения
- Пользователь не испытывает необходимости в дополнительной информации
- Пользователь может сравнить статусы разных элементов

### 5.3. Decision Support Success (Успех в поддержке принятия решений)

**Критерий:** Пользователь может принять обоснованное решение о приоритетах обслуживания на основе отображаемой информации.

**Измеримые показатели:**
- Время до принятия решения о приоритетах (должно быть < 30 секунд для Home, < 2 минут для Items)
- Процент правильных решений о приоритетах (должен быть > 85%)
- Отсутствие необходимости в дополнительных вычислениях или интерпретациях

**Качественные показатели:**
- Пользователь чувствует уверенность в принятом решении
- Пользователь не испытывает сомнений в правильности приоритетов
- Пользователь может объяснить, почему один элемент важнее другого

### 5.4. Accessibility Success (Успех в доступности)

**Критерий:** Пользователи с различными способностями восприятия могут понять статус элемента.

**Измеримые показатели:**
- Процент пользователей с дальтонизмом, которые могут правильно определить статус (должен быть > 90%)
- Соответствие WCAG 2.1 Level AA (контраст, использование цвета)
- Отсутствие зависимости от одного способа передачи информации

**Качественные показатели:**
- Пользователи с различными способностями восприятия чувствуют, что информация доступна
- Пользователи не испытывают барьеров в понимании статуса
- Пользователи могут использовать приложение в различных условиях (яркий свет, грязный экран)

### 5.5. Context Appropriateness Success (Успех в уместности контекста)

**Критерий:** Статус оптимизирован для контекста использования (Home vs Items).

**Измеримые показатели:**
- На Home: все 5 элементов видны без скролла (для стандартных мобильных экранов)
- На Items: пользователь может просмотреть все элементы с комфортом (скролл допустим)
- Эмоциональный тон соответствует ожиданиям пользователя для каждого контекста

**Качественные показатели:**
- Пользователь чувствует, что Home оптимизирован для быстрого обзора
- Пользователь чувствует, что Items оптимизирован для детального изучения
- Пользователь не испытывает ощущения, что интерфейс неоптимизирован для контекста

### 5.6. Cognitive Load Success (Успех в когнитивной нагрузке)

**Критерий:** Статус не создает избыточной когнитивной нагрузки.

**Измеримые показатели:**
- Отсутствие дублирования информации (один сигнал = одна единица информации)
- Отсутствие конкуренции между визуальными элементами за внимание
- Время до понимания статуса соответствует ожиданиям пользователя

**Качественные показатели:**
- Пользователь не испытывает визуальной перегрузки
- Пользователь не чувствует необходимости "расшифровывать" статус
- Пользователь может легко запомнить визуальные паттерны статусов

## 6. Constraints Summary

### 6.1. Technical Constraints

1. **Mobile First:** Интерфейс должен работать оптимально на мобильных устройствах (ширина экрана 375-430px)
2. **Vertical Space:** На Home должно помещаться до 5 элементов без скролла
3. **Horizontal Space:** Ограниченное горизонтальное пространство на мобильных устройствах
4. **Performance:** Визуализация статуса не должна замедлять рендеринг или взаимодействие

### 6.2. Functional Constraints

1. **Dual Logic Support:** Статус должен поддерживать как km-based, так и calendar-based логику
2. **Prediction Reliability:** Статус должен индицировать надежность прогноза
3. **Status Categories:** Статус должен различать категории: критический, предупреждающий, нормальный, неизвестный
4. **Specific Values:** Статус должен предоставлять конкретные значения (количество дней) когда возможно

### 6.3. Accessibility Constraints

1. **Color Independence:** Информация о статусе не должна полагаться только на цвет
2. **Contrast Requirements:** Текст должен соответствовать WCAG 2.1 Level AA (контраст ≥ 4.5:1 для обычного текста)
3. **Readability:** Информация должна быть читаемой в различных условиях (яркий свет, грязный экран)
4. **Screen Reader Support:** Информация должна быть доступна для screen readers

### 6.4. Context Constraints

1. **Home Context:** Статус должен быть оптимизирован для быстрого обзора и приоритизации
2. **Items Context:** Статус должен быть оптимизирован для детального изучения и сравнения
3. **Emotional Tone:** Эмоциональный тон должен соответствовать контексту (спокойный на Home, информативный на Items)
4. **Information Density:** Плотность информации должна соответствовать контексту (компактная на Home, детальная на Items)

## 7. Principles Summary (Abstract)

### 7.1. Information Architecture Principles

1. **Uniqueness:** Каждый визуальный сигнал передает уникальную информацию
2. **Hierarchy:** Визуальные сигналы организованы в четкую иерархию важности
3. **Accessibility:** Информация доступна через множественные способы передачи
4. **Clarity:** Визуальные сигналы четкие и однозначные
5. **Consistency:** Визуальные сигналы консистентны, но адаптируются к контексту

### 7.2. Cognitive Load Principles

1. **Minimalism:** Минимальное количество визуальных сигналов для передачи необходимой информации
2. **Progressive Disclosure:** Общая информация доступна сразу, детальная — при необходимости
3. **Pattern Recognition:** Использование узнаваемых визуальных паттернов для быстрого распознавания
4. **Context Adaptation:** Адаптация визуального веса и плотности информации к контексту

### 7.3. User Experience Principles

1. **Glance Support:** Поддержка быстрого понимания статуса (glance mode)
2. **Detail Support:** Поддержка детального изучения статуса (detail mode)
3. **Decision Support:** Поддержка принятия обоснованных решений о приоритетах
4. **Emotional Appropriateness:** Эмоциональный тон соответствует контексту использования

---

**Примечание:** Этот документ определяет только цели, ограничения и принципы. Конкретные визуальные решения не включены, как и было запрошено.
